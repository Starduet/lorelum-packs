# 按读者下一步动作选择 reference、asset 或 script

## 适用场景

已经决定要给 Practice 配套补充材料、但尚未决定放进哪个 Pack 目录时使用。要判断的是读者下一步应当阅读、复制成任务产物，还是在明确授权下执行一个有边界的操作。

## 具体指导

需要按需阅读的长政策、字段表、证据说明、兼容矩阵或 runbook 放在 `references/`。要形成任务产物的报告骨架、清单、配置样板或起始文件放在 `assets/`，并要求读者先复制到目标工作区后编辑。重复且确定的诊断、检查或转换放在 `scripts/`；链接它的 Practice 必须说明何时使用、输入、预期输出和结束条件。

选能支持下一步动作的最小资源。脚本应便于检查；安装不能安装依赖、读取凭据、连接服务或自动执行脚本。目录与链接文字足以让读者推断唯一下一步、又不会把资源都理解为可执行指令时停止。需要有界的资源盘点时，可以在当前任务明确授权后，用 Pack root 作为唯一输入运行[资源清单辅助脚本](resource:scripts/inspect-resources.py)；它只输出 JSON 路径，不能代替 `lore validate`。

## 反模式

事故响应 Pack 把报告模板、长等级表和 Python 检查器都放入 `references/`，Practice 只说“使用事故资源”。读者可能打开错误文件、直接改已安装模板，或以为 Python 在安装期间已经运行。只改目录名并不能补上脚本输入和使用边界。

## 原因

三个目录给出不同的安全默认值：reference 是按需阅读，asset 是复制后编辑，script 是只在任务授权下显式运行。这样既不会无端加载上下文，也不会把脚本误解为自动权限。

## 例外与边界

asset 可以是二进制文件，script 也可以有未链接的 helper。静态 JSON 既可能作为证据被读取，也可能作为产物模板被复制；按下一步动作而不是扩展名分类。分类不代表脚本可信、被 sandbox 或跨环境可移植。`lore validate` 只检查结构，不运行脚本或证明其行为。

## 示例

部署审查 Practice 链接云服务兼容表、要求发布经理复制变更摘要骨架，并在公开 API 改动时链接确定性的 diff 检查器。Practice 写明 diff 范围和预期报告；安装和检索只保存脚本 bytes。每个文件位置都对应读者下一步动作。
