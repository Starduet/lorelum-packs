# 不同检查结果只能证明各自观察到的事情

## 适用场景

准备因为几项检查通过就说 Pack 可以使用或发布时，先看看每项检查究竟证明了什么。文件合法、领域专家认可内容、查询选对条目、Agent 照着作出好决定，是不同的结果。即使一起报告，也要分得清楚。

## 具体指导

把结果分开记录。结构检查可以确认 YAML 元数据、路径、ID 唯一性和目录覆盖；人工内容审查判断指导及决定所需上下文在该领域是否正确，而不是检查每条是否包含固定内容清单；召回测试记录特定系统面对明确查询时选了哪些 Practice，选中本身不能证明指导改善了决定。

评估额外价值时，用同一个强模型分别在不使用 Pack 和提供相关 Practice 的条件下完成有代表性的任务，并保持其他条件可比。记录任务、模型、Pack 修订、条件及观察到的决定结果，包括退步。每条结论都要说清依据哪一种结果、实际看到了什么。没做更进一步的测试，就不要把结论说得更宽；除非另有评估约定定义综合分数，否则不能把这些结果平均成质量分数。

## 反模式

无障碍 Pack 的格式校验通过，所有目录 ID 都有测试数据，文件也可解析。发布清单需要简单答案，结构结果又客观，作者便报告“指导完整且召回正确”。实际上没有无障碍专家审查内容、没有运行召回系统，也没有 Agent 任务使用这些指导。

## 原因

每类证据回答不同问题。混在一起会隐藏未知，也让后来者无法判断失败来自文件、内容、选择还是使用行为。

## 例外与边界

一个实验直接观察多个层级时，可以同时产生多类证据，但应分别记录。专家审查仍是判断，不等于召回行为；一次成功的 Agent 任务可以包含召回证据，却不能证明广泛的内容覆盖。本条只分类证据，不规定工具或基准测试规模。

## 示例

隐私 Pack 先通过 schema 与 ID 检查；两名隐私工程师发现删除条目的例外过宽并修正；随后召回测试区分了删除与保留查询；小型 Agent 任务又漏掉仓库特有审批步骤。作者分别报告四项结果，而不笼统称“Pack 已验证”。
