# 把资源完整性作为独立证据链验证

## 适用场景

改了 Pack 资源或 Practice 的 `resource:`
链接，不只要看本地有没有这个文件。路径是否合法，安装后有没有保留所选版本的文件，链接是否在需要时带到有用的材料，以及读者或 Agent 能否正确使用，都要分别确认。

## 具体指导

先对 Pack 运行
`lore validate`，记录 Pack 修订和结构诊断。它可以确认允许的资源路径与声明的链接在结构上有效，但不会运行脚本或评估脚本逻辑。对发布候选，通过受支持的 Registry 路径安装到隔离 Store，取回链接该资源的 Practice，并从返回的源文件根目录找到一个代表性参考文件或素材。记录准确版本、ref、文件地址，以及观察到的文件内容或身份。脚本只能在另一个已授权任务中、带明确输入和预期输出时运行。

再看读者只靠 Practice 本文是否仍能作出眼前的决定，链接是否在需要时才引导他们使用材料。哪些条目会被检索到、Agent 怎样使用它们，应分别测试。用[资源审阅清单](resource:assets/resource-review-checklist.md)记录实际观察了什么。每项声明都说清它覆盖结构、安装、内容审阅、检索选择、脚本执行还是 Agent 行为时，就可以停止。

## 反模式

可观测性 Pack 新增二进制仪表盘模板和日志解析脚本。`lore validate`
本地通过后，作者用一个日志文件跑了脚本，发布说明便声称 Pack“交付了验证过的可观测性自动化”。这没有安装所选发布版，没有证明 Practice 会在恰当的事故中引导读者使用它，也没有证明另一个 Agent 能安全地用解析器处理生产输入。

## 原因

资源比普通 Practice 文本多出两个要求：安装的发布版必须包含预期文件内容，Practice 也必须告诉读者何时需要这些文件。结构校验、从远程安装、检索、明确执行脚本和下游使用，观察的是这个过程的不同部分。

## 例外与边界

不要求每个辅助文件都直接被链接或执行。未直接链接的辅助文件可以结构合法，二进制素材可以用摘要或大小确认，不必在文本终端显示。成功安装不证明脚本可用；成功运行脚本不证明发布产物包含它。不要为了补齐发布清单而执行脚本。

## 示例

数据迁移 Pack 新增兼容性参考、迁移计划模板和只读 schema 差异脚本。作者记录无诊断的 `lore validate`
结果，把带 tag 的发布版安装到隔离 Store，从获取到的 Practice 返回的源文件根目录读取参考文件，并确认模板存在。另一个已授权测试再用测试数据运行差异脚本。检索查询和 Agent 练习单独报告，因此发布声明只覆盖实际验证过的链接和文件内容。
