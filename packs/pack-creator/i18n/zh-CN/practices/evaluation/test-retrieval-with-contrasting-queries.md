# 用应该匹配和不该匹配的查询一起测试召回

## 适用场景

权威 Practice 已经写得比较稳定，就试试几条内容都看似相关时，召回系统能否选对。必须实际运行查询、看这个系统返回什么；目录覆盖或人工内容审查不能代替这项观察。

## 具体指导

为每条重要 Practice 准备一个直接查询、一个不复制标题的自然改写、一个不应选中的近似查询，以及一个指向最相近的另一条 Practice 的查询。运行前写出预期选择或不选择，使用未来读者或 Agent 的真实说法，同时检查漏选和看似合理的错选。只有观察到的混淆来自 Practice 设计时，才修改触发条件或拆并内容；不要为迁就已知的召回系统缺陷而改内容。在有代表性的对比中能区分重要相邻条目时停止，多加简单正向查询不会增强结论。

## 反模式

安全日志 Pack 分别有“设计事件时选择字段”和“输出日志时保护敏感值”。作者为尽快完成，只测试“安全日志应包含哪些字段”及类似标题改写，目标条目每次都出现。没有查询“现有 logger 暴露 session
token 怎么办”，因此评估从未发现字段设计条目会压过脱敏条目。

## 原因

正向查询只证明一条 Practice 能被找到，不能证明系统知道它何时是错误答案。对比查询才能显示触发条件和相邻条目的区别是否足以支持正确选择。

## 例外与边界

自动评估尚未建立时，可先做少量人工对比，但要标为有限观察。产品只要求返回正确的几条结果时，不必规定精确排名，仍应排除会误导行动的相邻条目。查询数量、目录覆盖和测试数据有效，都不能单独证明召回质量。

## 示例

运维 Pack 分别处理“设置延迟告警阈值”和“诊断已触发告警”。作者预先写四个预期：“选择 p95 阈值”和“这个延迟告警应多敏感”应选前者；“部署后告警正在触发，哪里变了”不应选；“调查反复延迟通知”应偏向诊断。运行后发现一个含糊
`applies_when`，收窄后结束。
