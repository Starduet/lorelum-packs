# 声称发布前先走通用户真正使用的安装路径

## 适用场景

不可变的发布候选和 Registry 条目都已存在，先按告诉用户的方式完整安装一次，再说 Pack 已发布、可安装或可通过受支持的命令获取。要检查的是这个准确版本从 Registry 到安装完成的整条路径。内容质量、召回表现、Agent 是否受益，仍需其他证据。

## 具体指导

使用隔离目标目录和对用户公开的同一安装路径。经预期 Registry 仓库解析 Pack，确认版本和发布 ref；从该来源获取受支持的 Pack 文件，通过 Pack 解码和校验，安装到目标 Store，再读回 Pack 身份和预期 Practice
ID。记录解析出的 commit、版本、命令或 API 路径、环境和结果。ref 缺失或可移动、远程来源与已审查候选不一致、文件遗漏、解码失败或安装身份错误时，都不能声称发布可用。准确版本的一条代表性受支持路径成功，加上发布策略要求的平台检查后停止；重复安装次数不能变成语义质量分数。

若发布版包含 Pack 资源，再取回一条链接代表性文件的 Practice，从返回的 Pack 根目录找到链接目标，记录地址与观察到的文件内容或摘要。这只能证明所选发布产物保留了该文件，不会运行脚本，也不证明召回质量。

## 反模式

事故告警 Pack 的本地目录校验通过，目录文件齐全，README 也写了官方安装命令。发布日期临近，合并后打 tag 看似例行工作，作者便宣布
`0.1.0` 可安装；实际 Registry
ref 拼错且远程不存在。所有本地内容检查仍绿，用户却无法按文档路径取得 Pack。

## 原因

用户安装发布版会经过 Registry 解析、不可变 ref、远程对象获取、解码和 store 安装，任何一层都可独立失败。走通这条链只支持“可安装”声明，不证明其他质量。

## 例外与边界

私有或离线 Registry 可要求专用环境和凭据，应验证文档规定的路径且不泄露密钥。ref 尚不存在时，可以明确称草稿“本地有效”。成功安装不证明 Practice 清楚、能匹配正确查询或改善 Agent 决定，安装条目数也不证明覆盖。

## 示例

前端性能 Pack 已完成人工审查并打发布 tag。维护者在干净临时 Store 中，通过官方 Registry 名称安装，而不是直接读工作树。结果解析到已审查 commit 和版本，获取预期权威路径下的文件，通过解码，并读回 Pack 与 Practice
ID。此后只声明该版本可安装，语义审查和召回测试仍分别报告。
