# 内容变化要发布为可追溯的新版本

## 适用场景

已接受的权威内容准备发布，或已发布版本需要纠正时，用一个新的、固定不变的版本标识这批准确文件。重要规则也要让审查者查得出：来自公开资料、反复观察到的需求，还是明确标注的作者综合判断。用户能否实际安装这个版本，仍需另行检查。

## 具体指导

把发布候选固定到一个 commit。已有版本发布后权威指导发生变化，应创建新版本和新发布 ref，不能移动旧 tag 或替换文件。发布对象准备好后，再让 Registry 条目和发布说明指向该版本。来源记录应让人区分原文明确要求、反复观察到的失败和作者推广判断，不能把综合判断写成实测效果。即使只改措辞或资源文件内容，也要保留版本边界：措辞会改变召回，只改资源也会改变所选发布产物。记录本次改变的是权威 Practice 内容、仅
`references/`、`assets/` 或 `scripts/`
文件内容，还是两者兼有。版本、commit、发布 ref、权威文件、资源树和来源记录都能确认同一份可复现的发布产物时，就可以停止；下一步再证明它能安装。

## 反模式

网络安全 Pack 的 `1.0.0` 已打 tag，维护者发现一条 TLS
Practice 推荐过时 cipher。只改一段却要新版本、Registry 行和 release
note 看似太重，于是移动旧 tag。相同版本在不同日期会得到不同指导，来源又只写“行业最佳实践”，无法判断来自当前供应商文档还是作者判断。

## 原因

Pack 内容会改变 Agent 决定，所以旧版本必须持续表示相同文件内容和指导。即使 Practice 摘要不变，只更新资源也会改变下次定位到的参考文件、素材或脚本。清楚的来源记录让审查者判断规则依据和局限，不把合理综合误认成 Pack 有效性的公开证明。

## 例外与边界

未发布草稿在没有 Registry 发布或不可变 ref 承诺时可以原地修改。损坏 tag 或误暴露密钥要按仓库治理和事故流程处理，不能为不可变性保留有害数据。普通句子不必逐条引用，但重要主张和综合判断的范围必须可审查。版本化发布对象不证明语义质量或可安装性。

## 示例

运维 Pack 根据新公开响应政策调整事故严重等级，又发现两条旧 Practice 会竞争同一升级决定。作者引用政策中的明确响应时间，把拆分边界标为 Pack 写作综合，并在新 commit 和版本发布；旧 tag 不变，既保持旧安装可复现，也让审查者看出哪些来自政策、哪些来自设计判断。
