# 内容变化要发布为可追溯的新版本

## 适用场景

已接受的 canonical 内容准备发布，或已发布内容需要纠正时使用。要决定哪个不可变版本包含这些准确文件，以及审查者怎样追踪重要规则来自公开来源、反复观察到的需求，还是明确标注的作者综合判断。是否真能安装另行验证。

## 具体指导

把发布候选固定到一个 commit。已有版本发布后 canonical 内容变化，应创建新版本和新 release
ref，不能移动旧 tag 或替换文件。发布对象准备好后，Registry 和 release
note 只指向该版本。来源记录应让人区分原文明确要求、反复失败观察和作者推广判断，不能把综合写成实测效果。即使只改措辞或 resource bytes，也要保留版本边界：措辞会改变召回，而只改 `references/`、`assets/` 或 `scripts/` 也会改变读者定位到的 artifact。记录本次变更是 canonical Practice 内容、资源 bytes，还是两者兼有。版本、commit、ref、canonical 文件、资源树和来源记录共同指向一个可复现对象时停止；安装证明下一步再做。

## 反模式

网络安全 Pack 的 `1.0.0` 已打 tag，维护者发现一条 TLS
Practice 推荐过时 cipher。只改一段却要新版本、Registry 行和 release
note 看似太重，于是移动旧 tag。相同版本在不同日期会得到不同指导，来源又只写“行业最佳实践”，无法判断来自当前供应商文档还是作者判断。

## 原因

Pack 内容会改变 Agent 决定，所以旧版本必须持续表示相同字节和指导；即使 Practice digest 不变，只更新资源也会改变下次读取定位到的 reference、asset 或 script。清楚来源让审查者判断规则依据和局限，不把合理综合误认成 Pack 有效性的公开证明。

## 例外与边界

未发布草稿在没有 Registry
release 或不可变 ref 承诺时可以原地修改。损坏 tag 或误暴露 secret 要按仓库治理和事故流程处理，不能为不可变性保留有害数据。普通句子不必逐条引用，但重要主张和综合边界必须可审查。版本化对象不证明语义质量或可安装性。

## 示例

运维 Pack 根据新公开响应政策调整事故严重等级，又发现两条旧 Practice 会竞争同一升级决定。作者引用政策中的明确响应时间，把拆分边界标为 Pack 写作综合，并在新 commit 和版本发布；旧 tag 不变，既保持旧安装可复现，也让审查者看出哪些来自政策、哪些来自设计判断。
