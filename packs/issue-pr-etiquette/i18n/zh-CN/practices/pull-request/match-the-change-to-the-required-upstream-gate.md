# 按变更类型完成必需的前置流程

## 适用场景

写代码前，先看这次变更能否直接提 PR，还是需要先在 issue 或设计文档中取得同意。按仓库自己的流程办，尤其是要改变其他工作所依赖的接口或行为时。

## 具体指导

先读贡献指南。改变其他工作所依赖的公开 schema、接口、评估行为或协议时，要先在 issue 中明确要改什么并达成共识，再开始实现。仓库要求设计文档时，也要先准备好。

不改变这些约定的局部修复可以直接提 PR，但正文仍须说明根因、具体修了哪些内容，以及如何验证。如果不确定是否需要先建 issue 或取得设计批准，就先弄清楚再写代码，必要时到 issue 区询问。必需的前置步骤都完成了，或已确认仓库不要求这些步骤后，才开始动工。

## 反模式

Agent 因为 diff 很小，把评估器评分行为的改动直接写进 PR。评审卡在“这是在哪达成共识的？”：三个下游测试套件依赖旧行为，讨论不得不在 diff 里逐行展开，而不是集中在一个 issue 中。反过来也会出错：错字修复在为契约变更设置的 issue 审批流程中等了好几周。

## 原因

先有 issue 和设计决定，团队才能在影响下游工作之前同意变更。跳过这些要求，设计讨论就会移到 diff 评审中，评审者不得不一边看代码一边重新讨论范围。琐碎修复也走同样的流程，会浪费评审时间，让贡献者逐渐不再遵守流程。

## 例外与边界

各仓库定义自己的紧急处理流程。规则允许时，紧急回滚或热修可以先合并、随即补 issue；顺序以仓库规则为准。纯文档修复通常要求更少的前置步骤，具体由贡献指南而非本条决定。在没有声明流程的仓库贡献时，改变其他工作所依赖的约定，仍以先建一个关联 issue 为稳妥默认。

## 示例

修改测试评估器的评分逻辑之前，贡献者确认其他工作依赖这套行为，于是先提交一个聚焦该行为变更的 issue，并等待流程要求的 issue 或设计批准。同一天的 README 错字直接提 PR，正文写明根因、单文件修复边界，以及用来验证的文档渲染检查。
