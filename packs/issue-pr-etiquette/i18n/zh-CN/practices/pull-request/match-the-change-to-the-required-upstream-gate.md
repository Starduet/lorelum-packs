# 让变更对上它需要的上游门禁

## 适用场景

一个变更即将动工，贡献者必须判断：仓库流程是否要求先有 issue 或设计对齐，还是可以直接提 PR 时使用。

## 具体指导

查贡献指南里什么会触发先决 issue 或设计工件。改变其他工作所依赖内容的变更——公开 schema、接口、评估语义、协议——先提交收敛性的 issue，流程要求设计工件时先产出它，然后才实现。不改变契约的局部修复可以直接提 PR，但直通路线自带义务：PR 正文必须写明根因、修复边界和验证方式。类别不清楚时，先分类再写代码——在 issue 区问一句比重新评审便宜。当变更对应唯一门禁、且该门禁要求的工件已存在或确定不需要时停止。

## 反模式

Agent 因为 diff 很小，把评估器评分语义的改动直接写进 PR。评审卡在"这是在哪达成共识的？"——三个下游套件依赖旧语义，辩论在 diff 里逐行进行，而不是在单个 issue 的设计讨论里。反向失败同样常见：一个错字修复在为契约变更设计的 issue 审批流程后面排了好几周。

## 原因

门禁设在下游工作依赖稳定性的地方；跳过门禁会把设计辩论搬进最贵的场所——diff 评审——每位评审者都要重判一次范围。把重门禁套在琐碎修复上则把同样的评审产能花在零收益上，强制流程就是这样被悄悄废弃的。

## 例外与边界

各仓库定义自己的紧急路径——紧急回滚或热修可以先合并、随后按规则要求的顺序立刻补 issue。纯文档修复通常走更轻的门禁；由贡献指南而非本条定义是哪种。在没有声明流程的地方贡献时，契约类变更配一个链接 issue 仍是安全默认。

## 示例

改测试评估器的评分逻辑之前，贡献者先分类：评分语义属于契约类，于是先提交一个收敛到单一行为变更的 issue，等流程要求的变更工件通过校验。同一天的 README 错字走直通 PR，正文写明根因、单文件修复边界和用来验证的文档渲染检查。
