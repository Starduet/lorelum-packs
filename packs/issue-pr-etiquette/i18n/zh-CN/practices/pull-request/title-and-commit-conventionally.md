# 按约定格式写标题与提交

## 适用场景

仓库的历史遵循类型化的约定格式（最常见是 Conventional
Commits），或贡献指南明确指定了命名规范，此时为提交信息或 PR 标题命名时使用。这里的决策是主题行的确切形态、以及什么内容应放进正文而非主题行。仓库明确采用另一种命名风格时不适用本条——那时遵循那种风格。

## 具体指导

严格遵循声明的约定：类型、可选 scope、冒号，然后是祈使语气、小写的主题，长度在该约定的限额内（常见 72 字符），陈述变更做了什么而不是制作它的过程。一次提交一个逻辑变更；把原因、权衡和 issue 链接放进提交正文或 PR 正文，不放进主题行。仓库采用 squash 合并时，PR 标题会成为提交，同一条规则约束它。当
`log --oneline` 不打开任何 diff 就能读作一份"改了什么"的变更日志时停止。

## 反模式

合并进历史的是 "fixes"、"update stuff"、"final
changes"、"wip"。半年后，贡献者检索改动物包校验的那个变更，一无所获；解析类型化主题的变更日志脚本产出一个空版本；blame 指向一条能描述半个仓库的主题。

## 原因

历史是一个检索界面。类型化、祈使、带 scope 的主题让人和工具都能按种类和区域找到变更、生成发布说明、不开 diff 就读懂仓库演化；随手写的主题把这份索引抹掉了，对作者也毫无收益。

## 例外与边界

仓库声明的变体优先——不同的类型集合、大写主题或工单前缀覆盖通用形态。平台生成的合并提交有自己的格式，不属于作者主题。私有分支上的进行中提交可以随意；约定约束的是别人将阅读的历史，所以仓库流程期望时，开 PR 前先 squash 或改写。

## 示例

给包引擎加资源协议的 PR 标题为
`feat(pack): add resource protocol support`——类型、scope、祈使小写主题，41 个字符。正文承载设计理由和关联 issue。姊妹错字修复以
`docs(readme): fix install command flag` 落地，一年后两者都能被 `git log --grep 'resource support'`
找到。
