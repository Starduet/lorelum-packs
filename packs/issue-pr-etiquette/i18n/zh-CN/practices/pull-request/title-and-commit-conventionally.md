# 按约定格式写标题与提交

## 适用场景

仓库的提交历史或贡献指南采用带类型前缀的命名格式时，提交主题和 PR 标题都按它来写，不要另起一套风格。Conventional
Commits 很常见，但仓库自己的规定优先；明确采用其他风格的，就遵循那个风格。

## 具体指导

严格遵循仓库声明的约定。常见格式是类型、可选范围（scope）、冒号，再接祈使语气的小写主题，长度不超过规定上限（常见为 72 字符）。仓库规定了其他类型、大小写或前缀时，以它为准。

主题写清改了什么，不讲修改过程。一次提交只包含一个逻辑变更，原因、权衡和 issue 链接放进提交正文或 PR 正文。采用 squash 合并的仓库会把 PR 标题用作提交主题，因此标题也要按同样的格式写。读者只看
`log --oneline`，就应能知道各次提交改了什么，不必打开 diff。

## 反模式

合并后的历史写着 "fixes"、"update stuff"、"final
changes"、"wip"。半年后，贡献者检索修改包校验逻辑的变更，却一无所获；解析带类型前缀主题的脚本生成了空的发布日志；blame 指向的提交主题能描述半个仓库。

## 原因

人和工具会搜索提交主题来查找变更、生成发布说明，并在不打开 diff 的情况下了解历史。类型、可选范围和祈使主题让这些搜索有用；含糊主题则让读者无法区分不同变更。

## 例外与边界

仓库声明的变体优先：不同的类型集合、大写主题或工单前缀都覆盖通用格式。平台自动生成的合并提交使用自己的格式，不属于作者编写的主题。私有分支上的未完成提交可以随意；约定约束的是别人将阅读的历史，因此仓库流程有要求时，开 PR 前先 squash 或改写主题。

## 示例

给包引擎添加资源协议的 PR 标题为
`feat(pack): add resource protocol support`，包含类型、范围、祈使小写主题，共 41 个字符。正文说明设计理由并链接相关 issue。另一处错字修复的标题为
`docs(readme): fix install command flag`。一年后，通过
`git log --grep 'resource protocol' --grep 'install command'` 可以找到这两个提交。
