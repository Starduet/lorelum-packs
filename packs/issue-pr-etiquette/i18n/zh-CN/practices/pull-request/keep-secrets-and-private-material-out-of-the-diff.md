# 不让机密与私密材料进入 diff

## 适用场景

变更触碰配置、日志、fixture、测试数据、示例输出或从私有系统复制的材料，diff 即将公开请求评审时使用；起草任何引用日志或数据的公开帖子时同样适用。这里的决策是：diff 与引用材料按当前写法是否可公开。仅凭怀疑就应触发本条——核实怀疑属于修复，不属于检查。

## 具体指导

逐行扫描所有新增内容中的访问令牌、API
key、密码、连接串、内部主机名、客户标识符和真实个人数据；同时扫描引用的日志、fixture 文件和示例输出——它们和配置一样容易泄漏。把真实值替换为合成占位符（`internal.example`、`user-1234`、`ssh-key-ed25519-REPLACED`），机密从环境变量或平台机密库加载。机密一旦被推送到任何公开位置，就按已泄漏处理：先轮换，再走仓库的移除流程——重写历史撤不回爬虫已经复制走的内容。当你能解释 diff 里每个可疑字符串为何是合成的或公开的时停止。

## 反模式

为了让失败的集成测试可复现，贡献者把真实内部端点和一枚有效令牌粘进 fixture。PR 是公开的，自动化爬虫一小时内就读到了。令牌第二天轮换了，但内部主机名和拓扑结构永远留在缓存和 fork 里，这起事故损失的好感远超那个测试节省的时间。

## 原因

公开的 diff 会被爬虫、镜像和 fork 立刻且永久地复制——删除和 force-push 都撤不回。消毒也在保护数据里的人：fixture 里的客户标识符与个人记录，比它们举例的那个 bug 活得久。最后一遍检查很便宜；它下游的每一个后果都不便宜。

## 例外与边界

公开即设计的标识符——公开文档 URL、已发布的示例值、本就公开的包名——保持原样。对机密的引用（环境变量名、机钥库的 key）不是机密，应该在 diff 里；值才不该。私密评审渠道能降低暴露但不改变这项检查，因为材料通常在合并后照样公开。

## 示例

请求评审前，作者重读 diff，发现粘贴的错误信息里有真实的内部主机名。他替换成
`internal.example`，把 fixture 令牌换成合成值，确认占位符下测试仍能复现，并在 PR 正文 checklist 项里注明已消毒。干干净净地上线。
