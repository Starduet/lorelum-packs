# 不让机密与私密材料进入 diff

## 适用场景

任何 PR 在请求评审前，都要检查 diff 是否含有私密信息，尤其留意配置、日志、测试样例（fixture）、测试数据、示例输出和从私有系统复制的材料。公开帖子要引用日志或数据时，也要先检查。即使只是怀疑某个值不能公开，也要查清楚再发布。

## 具体指导

逐行检查所有新增内容，查找访问令牌、API
key、密码、连接串、内部主机名、客户标识符和真实个人数据。引用的日志、fixture 文件和示例输出也要看，它们和配置一样容易泄漏信息。把真实值换成虚构占位值（`internal.example`、`user-1234`、`ssh-key-ed25519-REPLACED`），机密从环境变量或平台机密库加载。

机密一旦被推送到任何公开位置，就按已泄漏处理：先轮换，再走仓库的移除流程。重写历史撤不回爬虫已经复制的内容。检查完成时，你应能说明 diff 中每个可疑字符串为什么是虚构值或已经公开的信息。

## 反模式

为了让失败的集成测试可复现，贡献者把真实内部端点和一枚有效令牌粘进 fixture。PR 是公开的，自动化爬虫一小时内就读到了。令牌第二天轮换了，但内部主机名和拓扑结构永远留在缓存和 fork 里，这起事故损失的好感远超那个测试节省的时间。

## 原因

公开的 diff 即使被删除或 force-push 覆盖，也可能继续留在爬虫、镜像和 fork 中。发布前去除敏感值，也是在保护数据涉及的人：客户标识符和个人记录可能比它们所说明的 bug 留存得更久。发布前检查，可以避免事后删除也无法撤销的泄漏。

## 例外与边界

本来就供公开使用的标识符，如公开文档 URL、已发布的示例值和公开包名，保持原样。对机密的引用，如环境变量名或机密库中的键名，不是机密，可以保留在 diff 中；不应保留的是实际值。私密评审渠道能降低暴露程度，但不能省略检查，因为材料通常仍会在合并后公开。

## 示例

请求评审前，作者重读 diff，发现粘贴的错误信息里有真实内部主机名。他将其换为
`internal.example`，把 fixture 令牌换成虚构值，确认使用占位值后测试仍能复现问题，并在 PR 正文的检查清单中注明已去除敏感信息，然后才提交 PR。
