# 为陌生评审者撰写 PR 正文

## 适用场景

即将打开一个 PR，作者必须写出一份让完全没有作者上下文的评审者不用先提问就能核验变更的正文时使用；正文因重大变更需要更新时同样适用。仓库没有提供模板时，从
[pull request 模板](resource:assets/pull-request-template.md)起步。

## 具体指导

为一位没读过 issue 串、没看过聊天讨论、也不知道你本地尝试过程的评审者而写。包含：摘要——改了什么、以及刻意不改变什么；本 PR 解决的关联 issue；变更类型，有破坏面时点名破坏面；如何测试——逐字列出你运行的命令加上你演练过的具名场景，而不是"本地测过"这类形容词；仓库模板要求的 checklist；给评审者的备注——设计意图和刻意推迟的内容。无 issue 的直通修复 PR，正文还要额外承担根因、修复边界与验证——这些义务不能转交给被链接的讨论。当陌生读者仅凭正文就能回答"这个变更声称做什么、我如何核对"时停止。

## 反模式

PR 正文写着"如前所述"和"见标题"。评审者面对两百行 diff 却没有任何预期行为的陈述，靠意外才发现一个破坏性的 JSON 字段变更，把评审时间花在逆向还原范围而不是核验范围上。即便最终批准，那张批准书认证的也是评审者的重构——不是作者的意图。

## 原因

评审者最先问的是：变更声称什么、如何核验。自足的正文把评审从考古变成"拿声明的主张对照 diff"，在合并前而非合并后抓住范围误解，并把验证证据留给日后从历史里翻到这个 PR 的读者。

## 例外与边界

单文件修复也需要一句摘要加一句验证；小不是豁免，只是更短。超大规模的移植可以链接设计文档取深度，但正文仍须用自己的话概括变更与验证。模板各节是下限不是上限——补充变更需要的节，但仓库要求的节一节都不能删。

## 示例

一个加资源协议的 PR 开篇两段摘要，其中一句写明资源"刻意不影响"什么，链接
`Closes #161`，勾选新特性和破坏性变更并注明必填字段，列出从 `bun test` 到 `git diff --check`
的五条逐字命令，走过六个具名回归场景，最后用备注告诉评审者哪些设计决策在范围之外。对 diff 的评审第一个小时就开始了。
