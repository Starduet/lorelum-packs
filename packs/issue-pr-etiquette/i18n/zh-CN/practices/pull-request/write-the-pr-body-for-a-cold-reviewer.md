# 为不了解背景的评审者撰写 PR 正文

## 适用场景

开 PR 时，向没跟进过这项工作的人说明改了什么、怎样核对；变更有重大调整后，也要更新正文。仓库没有提供模板时，从[pull request 模板](resource:assets/pull-request-template.md)起步。

## 具体指导

为没读过 issue 讨论、没看过聊天记录、也不知道你本地尝试过程的评审者写正文。包含：

- 变更摘要：改了什么，以及刻意没改什么。
- 本 PR 解决的关联 issue。
- 变更类型，以及任何不再兼容旧用法的接口或行为。
- 测试方式：原样列出运行过的命令，写明检查过的具体场景，不要只说“本地测过”。
- 仓库模板要求的检查清单。
- 给评审者的备注：设计意图，以及刻意留待后续处理的内容。

直接提交没有关联 issue 的修复时，正文还须说明根因、具体修了哪些内容，以及如何验证，不能只给讨论链接。不了解背景的评审者，应当仅凭正文就能知道你声称这个 PR 做了什么、该怎样核对。

## 反模式

PR 正文写着“如前所述”和“见标题”。评审者面对两百行 diff，却找不到预期行为的说明，偶然才发现一个破坏兼容性的 JSON 字段变更，只能把评审时间花在还原范围而非核验范围上。最终批准的也是评审者自行推断的范围，不一定是作者的意图。

## 原因

评审者最先问的是变更声称做什么、如何核验。正文交代完整，他们就能把这些说明与 diff 对照，而不必猜测作者意图。这能在批准前暴露范围误解，也能为日后从历史中找到这个 PR 的读者保留验证证据。

## 例外与边界

单文件修复也需要一句摘要加一句验证说明；小变更只是写得更短，不是免写。大规模移植可以链接设计文档提供细节，但正文仍须用自己的话概括变更和验证情况。模板只是最低要求：可以补充变更需要的小节，但不能删除仓库要求的小节。

## 示例

一个添加资源协议的 PR 开篇有两段摘要，其中一句写明资源刻意不影响什么，链接
`Closes #161`，勾选新特性和破坏性变更，并注明必填字段。正文原样列出从 `bun test` 到
`git diff --check`
的五条命令，说明检查过的六个回归场景，最后备注哪些设计决策不在范围内。对 diff 的评审在第一个小时就开始了。
