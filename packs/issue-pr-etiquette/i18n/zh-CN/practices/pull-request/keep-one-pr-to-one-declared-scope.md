# 一个 PR 只保留它声明的一个范围

## 适用场景

正在组装 PR，或工作中发现相邻的、值得顺手修的问题，diff 或诱惑可能超出 PR 标题声明的单一变更时使用。机械性的全仓变更本身就是一种声明的单一范围，不适用本条。

## 具体指导

让 PR 标题声明一个范围，然后让每个 hunk 对它负责：只有"回滚本 PR 就应随之消失"的 hunk 才属于它。克制住把顺手发现的小东西——无关错字、过期测试、诱人的重构——折叠进来的冲动，每一件单独提交变更，再小也一样。仓库惯例是 one
issue per
PR 时，只链接本 PR 解决的那个 issue，兄弟 issue 留给兄弟 PR。发现的问题阻塞当前变更时，只修解锁所需的最小部分，其余立件跟踪。当 diff 读起来是一个可评审的整体、其移除或回滚是一次单一决策时停止。

## 反模式

修复越界错误时，贡献者顺手重排了周围模块的格式、升了一个"早该升"的依赖。这个 PR 现在背着三种风险；批准 bug 修复的评审者等于同时批准了三者，之后的回归无法二分定位到单一变更，回滚依赖升级还会把 bug 修复一起撕掉。

## 原因

评审、回滚、二分、cherry-pick 都以 PR 为粒度运作。单一范围意味着一次批准只覆盖一种风险、一次回滚是一次决策、历史保持可归因；混合范围悄悄把每次批准变成一揽子交易，还把无关的失败耦合在一起。

## 例外与边界

机械性清扫——格式化、重命名、codemod——作为"标题精确声明了该机械范围"的一个 PR 是正当的。拆开就无法编译或无法独立生效的变更（如 API 与仓内调用方）虽然触碰多个文件，仍是一个范围。极小的后续只有在仓库惯例明确允许搭车、且在正文中点名时才可以随行。

## 示例

修复中途，作者注意到邻近文件里一条拼错的日志和一段过期注释。他把修复控制在 -12/+4 行完成，然后为错字和注释各开了一个单行 PR，各自带一句验证说明。三个都在几分钟内过审；日后回滚修复时不牵连任何别的东西。
