# 一个 PR 只保留它声明的一个范围

## 适用场景

整理 PR 时，看看 diff 中的每处改动是否都属于标题所说的那件事。工作中又发现值得修的问题，也先这样判断。涉及很多文件不等于范围过大，全仓机械性修改本身就可以是一件事。

## 具体指导

用标题说清这个 PR 要改什么，再逐块看 diff：如果回滚整个 PR，这块改动是否也应该撤销？顺手发现的无关错字、过期测试或重构，无论多小，都单独提交。仓库要求一个 PR 对应一个 issue 时，只链接本 PR 解决的那个 issue，其他 issue 留给其他 PR。

如果另一个问题让当前变更无法完成，只修到足以解除阻塞，其余另开 issue。保留下来的改动，应当能一起批准，也能一起回滚，而不牵连无关改进。

## 反模式

修复越界错误时，贡献者顺手重排了周围模块的格式、升了一个"早该升"的依赖。这个 PR 现在背着三种风险；批准 bug 修复的评审者等于同时批准了三者，之后的回归无法二分定位到单一变更，回滚依赖升级还会把 bug 修复一起撕掉。

## 原因

只保留一个范围，评审者就能批准所需变更，而不必同时接受无关工作。维护者也能独立回滚或挑选合入（cherry-pick）它，并追查哪个变更引入了回归。范围混在一起，就会迫使这些决定一起做，即使失败原因毫不相关。

## 例外与边界

格式化、重命名、codemod 等机械性批量修改可以放在一个 PR 中，只要标题准确声明这个范围。拆开就无法编译或无法正常工作的变更（如 API 与仓内调用方）虽然涉及多个文件，仍是一个范围。极小的后续改动只有在仓库惯例明确允许时才能随行，而且必须在正文中点名。

## 示例

修复中途，作者注意到邻近文件里一条拼错的日志和一段过期注释。他把修复控制在 -12/+4 行完成，然后为错字和注释各开了一个单行 PR，各自带一句验证说明。三个都在几分钟内过审；日后回滚修复时不牵连任何别的东西。
