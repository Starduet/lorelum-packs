# 用可检验的验收标准把问题收敛为单一问题

## 适用场景

即将提交一个会被跟踪、指派或排期的 bug 或功能 issue 时使用。这里的决策是：该 issue 拥有的单一问题是什么、边界在哪里、什么可观察的结果算作已解决。未被跟踪、已转入讨论区的问题，或小到仓库流程允许直接提 PR 的变更，不适用本条。

## 具体指导

在标题和开头段落只陈述一个问题。写明它的边界（影响什么、明确不影响什么）、对其他工作的依赖、修复必须满足的验证要求。验收标准写成 checklist，每一项都必须能由非作者本人检验：一条应成功的命令、一份应存在的文档、一种应可观察的行为。凡是能被独立评审、合并或回滚的内容都拆出去——单独开 issue 并互相链接。从[功能 issue 模板](resource:assets/issue-template-feature.md)或[bug 报告模板](resource:assets/issue-template-bug.md)起步，删掉不为这个单一问题服务的段落。当每条验收标准都可客观检验、正文没有任何一段引入第二个交付物时停止。

## 反模式

团队提交了"改进搜索"，同时覆盖排序质量、索引管线和结果页 UI，完成标准只有一句"搜索变好用"。排序修复先合了，但 issue 关不掉，因为 UI 工作根本没开始。两个团队各自挂上自己的优先级，验收讨论在每次评审中重来一遍——没有人约定过"更好"观察的是什么。

## 原因

issue 是评审者接受、排期者排序、维护者关闭的基本单位。单一问题让这个单位可评审，可检验的验收标准让关闭变成一次核对而不是一轮谈判；混合的交付物会阻塞局部进展，并把验收问题埋进无关讨论里。

## 例外与边界

当每个子交付物都有自己的 issue 和验收标准、伞形 issue 只是跟踪它们时，伞形 issue 是正当的。探索性讨论在转为被跟踪 issue 之前可以宽泛——收敛发生在转换时，而不是在理解主题之前。验收标准可以引用规格或设计文档而不重抄，但 checklist 本身仍须能从该 issue 直接检验。

## 示例

贡献者注意到工具的真实使用持续暴露 fixture 从未覆盖的缺陷。他没有提"改进反馈"，而是提交了一个只拥有一个问题的 issue：缺少一条从真实使用回到维护者的隐私安全通道。边界排除存储与 schema 选型，验收标准是七条 checkbox——每条指明一份必须存在的文档或工作流必须做出的一种区分——维护者无需追问作者意图即可逐条核验。
