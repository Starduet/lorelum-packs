# 一个 issue 只解决一个问题，并给出可检验的验收标准

## 适用场景

准备提交需要跟踪、指派或排期的 bug 或功能 issue 时，先说明只想解决哪个问题，以及别人怎样判断它已经解决。未纳入跟踪的问题，继续放在已指定的讨论区；小变更若允许直接提 PR，也不必为了遵循本条而另开 issue。

## 具体指导

标题和开头段落围绕一个问题展开。说明影响什么、哪些内容不在这次范围内、依赖哪些其他工作，以及修复后必须怎样验证。验收标准写成检查清单，每项都应能由作者以外的人检验，例如一条应成功的命令、一份应存在的文档，或一种应能观察到的行为。

如果其中一部分可以独立评审、合并或回滚，就为它单独开 issue 并链接。从[功能 issue 模板](resource:assets/issue-template-feature.md)或[bug 报告模板](resource:assets/issue-template-bug.md)起步，删去无助于说明这个问题的部分。提交前，确认每条验收标准都有客观的检查办法，正文也没有带入另一件要交付的工作。

## 反模式

团队提交了“改进搜索”，同时覆盖排序质量、索引流程和结果页 UI，完成标准只有一句“搜索变好用”。排序修复先合并了，但 issue 关不掉，因为 UI 工作根本没开始。两个团队各自加上自己的优先事项，每次评审都要重新讨论验收，因为没有人约定过怎样检验“更好”。

## 原因

评审者接受 issue，团队安排其中的工作，维护者决定何时关闭它。只包含一个问题，才能把这些决定放在一起做。可检验的标准让维护者核对工作是否完成，而不是重新商量“完成”的含义；无关的交付物会让已解决主要问题的 issue 仍无法关闭，还会把验收问题埋进无关讨论里。

## 例外与边界

汇总 issue 可以跟踪多项工作，但每项都要有自己的 issue 和验收标准，汇总 issue 本身只负责跟踪。探索性讨论可以先谈得宽一些，等转为需要跟踪的 issue 时再明确一个问题，不必在尚未理解主题时就收窄。验收标准可以引用规格或设计文档，不必重抄，但读者仍须能从 issue 中的清单判断该怎样检验。

## 示例

贡献者注意到工具的真实使用持续暴露测试样例（fixture）从未覆盖的缺陷。他没有提“改进反馈”，而是提交一个只解决一个问题的 issue：缺少一条能保护隐私、将真实使用中的反馈传给维护者的通道。范围不包括存储与 schema 选型，验收标准有七个复选框，每项指明一份必须存在的文档或工作流必须区分的情况，维护者无需追问作者意图即可逐条核验。
