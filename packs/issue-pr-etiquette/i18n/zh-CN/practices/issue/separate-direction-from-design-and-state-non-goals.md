# 把方向与设计分开并写明非目标

## 适用场景

一个提案 issue 可能被当作实施计划来读，作者必须决定 issue 里承诺多少设计、显式排除什么时使用。缺陷报告（根因就是内容本身）或设计早已在别处敲定的变更不适用本条。

## 具体指导

陈述目标以及任何方案都必须满足的原则；实现选型不进入验收路径——除非某个决定已经做出，那时引用它在何处被决定，而不是当作新决定重述。加一个显式的非目标小节，写明你推迟的决策以及由谁、由什么流程来做。若仓库要求单独的设计工件，指向它，而不是把设计嵌进 issue。当读者不必先接受某种机制就能对目标表示赞同或反对、且每个被推迟的决策都被点名而非悄然缺席时停止。

## 反模式

一个"使用反馈"功能 issue 开篇就规定了存储 schema 和上传客户端。评审讨论塌缩进 schema 细节；两位本来认同需求的评审者因为反对存储选型而反对整个 issue。数月后规定的设计被证明是错的，团队只能重开一个已标记为"已接受"的 issue——没人说得清当时的共识到底覆盖了什么。

## 原因

issue 的"被接受"会被记忆为"对方向的共识"。机制一旦被焊死，评审者要拒绝设计就只能连目标一起拒绝；而一个被接受的 issue 会悄悄锁定从未被单独评估过的实施工作。点名非目标也避免评审者把沉默误读为"被推迟的决策已被考虑并作出"。

## 例外与边界

小型、机械性的提案可以正当包含其唯一显而易见的实现；当存在不止一个可信设计时这条边界才重要。上游已定的设计应作为既定背景被引用，而不是被当作非目标重新打开。非目标是推迟决策，并不禁止任何人提交推进该决策的后续 issue。

## 示例

一个隐私安全反馈回路的提案写明它"确立的是产品与治理目标，而非实现设计"，列出任何方案必须满足的七条硬原则，并以 out-of-scope 小节收尾——把存储、schema 与保留策略的选型推迟给未来的规格。评审者在 issue 里争论原则，把机制问题留给它该在的设计工件。
