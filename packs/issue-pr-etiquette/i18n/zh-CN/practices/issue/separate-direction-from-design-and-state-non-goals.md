# 把方向与设计分开并写明非目标

## 适用场景

提案有多种合理的实现方式时，让评审者先讨论目标，不必同时接受某一种设计。说明哪些选择已经确定，哪些还要再讨论。根因本身就是重点的缺陷报告，或设计早已在别处敲定的变更，不需要按这种方式拆开讨论。

## 具体指导

说明想达到什么目标，以及任何方案都必须满足的原则。不要把接受某种实现选型作为同意提案的条件；如果选型已经确定，就引用先前的决定。用非目标小节写清哪些决定留待后续，由谁或按什么流程决定。仓库要求单独的设计文档时，链接它，不要把设计塞进 issue。

读者应能在不接受某种具体实现的前提下，赞同或反对目标。留待后续决定的事项都要写出来，不能只是省略，让人误以为已经达成共识。

## 反模式

一个“使用反馈”功能 issue 开篇就规定了存储 schema 和上传客户端。评审讨论转向 schema 细节；两位本来认同需求的评审者因为反对存储选型而反对整个 issue。数月后规定的设计被证明是错的，团队只能重开一个已标记为“已接受”的 issue，没人说得清当时究竟同意了什么。

## 原因

接受 issue 通常意味着同意它的目标。如果 issue 同时要求采用某种实现，评审者就无法只拒绝设计而保留目标；接受提案也就让团队承诺了从未单独评估的选型。点名留待后续决定的事项，可以避免读者误以为这些选择已经确定。

## 例外与边界

小型、机械性的提案可以包含唯一显而易见的实现；有多个合理设计时，才需要分清这条边界。上游已定的设计应作为既定背景引用，不要重新列为待定的非目标。非目标只是推迟决策，不禁止另开后续 issue 来做出决定。

## 示例

一个能保护隐私的反馈通道提案写明它“确立的是产品与治理目标，而非实现设计”，列出任何方案必须满足的七条硬性原则，并在范围外事项小节中把存储、schema 和保留策略的选型留给后续规格文档。评审者在 issue 里讨论原则，把实现选型留给设计文档。
