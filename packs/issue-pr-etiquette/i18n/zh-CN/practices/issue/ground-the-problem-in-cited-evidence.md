# 用被引用的证据为问题立据

## 适用场景

issue 断言某件事损坏、缺失或值得做，作者在请求他人行动之前，必须决定什么具体证据支撑这一断言时使用。当证据本身涉密、不能出现在公开 issue 中时不适用本条——那时决策变成"什么可以安全地引用"。

## 具体指导

以触发该 issue 的具体事件开头：链接事故、失败运行、支持线程或早前 issue 编号，并引用能说明问题的最小片段。把观察到的事实与解读分开——先写发生了什么，再写你据此得出的结论。相关的早前 issue 逐条列出，各配一行角色说明（"证明该问题反复出现的证据"、"上一次尝试，因某原因被回滚"），而不是只丢一个编号。当主张基于你的推理而非观察到的事件时，明确写出依据是什么，让评审者能按提案而非事实来权衡它。当维护者顺着链接就能还原问题、无需再向你要例子时停止。

## 反模式

贡献者提交"检索经常返回不相关的 Practice"，没有任何链接。维护者请求给出示例查询；三天后贡献者补了两个案例，其中一个其实早已修复。这个 issue 的第一周花在收集证据而不是评估证据上，来回完成之前维护者既无法判断严重度，也无法查重。

## 原因

评审者按"能打开的证据"分诊，而不是按"被请求信任的信心"。引用让他们第一遍读完就能核实规模、查重并路由 issue；无引用的主张把分诊变成一轮轮追问，节奏慢的仓库永远问不完。

## 例外与边界

安全报告走仓库的私密 advisory 通道，不得携带公开复现步骤——引用 advisory 编号替代。全新提案可能没有先前事故：这个缺失本身就是陈述出来的依据，而不是编造证据存在的理由。引用的日志必须先消毒——本 Pack 把它视为"私密材料不得进入公开帖子"下的独立决策。

## 示例

一份"使用反馈通道"提案开头链接了两个真实任务暴露出 fixture 盲区的 issue，各引用一句话，然后列出五个相关 issue 及其角色——两个作为反复出现的证据，三个作为提案必须尊重的既有决策。维护者读完链接，确认模式真实存在，在第一条评论里就直接进入设计讨论，而不是先索要例子。
