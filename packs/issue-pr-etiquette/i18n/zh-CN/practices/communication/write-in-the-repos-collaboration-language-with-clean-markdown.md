# 用仓库声明的协作语言和整洁的 Markdown 写作

## 适用场景

写 issue、PR 正文、评审评论或重要状态评论时，先看贡献指南或治理文档是否声明了协作语言。说明文字用该语言，让协作者不必先翻译就能阅读。引用的日志、代码和上游文档保留原文。

## 具体指导

按仓库声明的协作语言写说明。例如，仓库可能规定协作者可见的帖子默认用中文，除非用户明确要求其他语言。文件路径、命令、代码标识符、错误信息和不可翻译的专有名词保留原文，方便检索。长帖可以用 Markdown 标题、段落和列表分开内容，让评审者能快速找到某节、引用具体某一行；短评论不必为此增加标题。写好后，熟悉该语言的读者应能很快找到需要的内容，每个标识符也都能按原拼写搜索到。

## 反模式

在一个默认中文的仓库里，Agent 因为 diff 是英文就把 PR 正文也写成英文，还在同一段里逐句切换语言。评审者每行都要慢下来，一条关于破坏性变更的关键注意事项在不熟悉的行文里被漏掉，之后用大家在讨论中使用的中文关键词检索时什么都搜不到。

## 原因

使用仓库声明的语言，能降低团队后续每次评审的阅读成本。标识符保留原拼写，读者就能在代码和文档中搜索、查看历史、顺着引用查找，而不必先猜它翻译前是什么。

## 例外与边界

用户明确要求其他语言时，该次对话遵循用户要求。向上游社区发帖时，遵循该社区的语言规范。多段长帖才需要标题和列表；两句话的评论不必加。引用材料保留源语言，并清楚标注为引用。

## 示例

贡献者用中文提交缺陷 issue：标题和所有解释性段落都是中文，而 `npm test`、文件路径
`src/validate/resources.ts` 和错误 `ENOENT: no such file or directory`
原样保留。评审者扫一眼标题就能定位，检索标识符直接命中正确文件。
