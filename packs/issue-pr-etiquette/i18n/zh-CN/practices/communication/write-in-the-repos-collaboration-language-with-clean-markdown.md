# 用仓库声明的协作语言和整洁的 Markdown 写作

## 适用场景

正在撰写会被协作者阅读的 issue、PR 正文、评审评论或重要状态评论，且仓库在贡献指南或治理文档中声明了工作语言时使用。这里的决策是散文部分用什么语言、帖子如何为陌生读者组织结构。语言由产物本身固定的内容（引用的日志、代码、上游文档）不适用本条。

## 具体指导

散文部分用仓库声明的协作语言写作——例如某个仓库在贡献指南里写明"协作者可见的帖子默认使用中文，除非用户明确要求其他语言"。文件路径、命令、代码标识符、错误信息和不可翻译的专有名词保留原文，不做翻译。用 Markdown 标题、段落和列表组织帖子，让评审者能扫读各节并引用具体某一行；一大段密不透风的文字也是一种结构选择，而且通常是错的。当声明语言的母语读者能在几秒内定位帖子任何一节、每个标识符仍可按原拼写检索到时停止。

## 反模式

在一个默认中文的仓库里，Agent 因为 diff 是英文就把 PR 正文也写成英文，还在同一段里逐句切换语言。评审者每行都要慢下来，一条关于破坏性变更的关键注意事项在不熟悉的行文里被漏掉，之后用大家在讨论中使用的中文关键词检索时什么都搜不到。

## 原因

声明的语言是整个团队都能流利阅读的语言；用它写作能降低其后每一次评审的成本。标识符保留原拼写才能在代码和文档中保持可检索，被翻译的标识符会悄悄破坏搜索、blame 和交叉引用。

## 例外与边界

用户明确要求其他语言时，该次对话遵循用户要求。有自己规范的上游社区保持其自己的语言。多段长帖才值得用标题和列表；两句话的评论两者都不需要。引用材料保留源语言并清楚标注为引用。

## 示例

贡献者用中文提交缺陷 issue：标题和所有解释性段落都是中文，而 `npm test`、文件路径
`src/validate/resources.ts` 和错误 `ENOENT: no such file or directory`
原样保留。评审者扫一眼标题就能定位，检索标识符直接命中正确文件。
