# 请求评审前先回读你发出的帖子

## 适用场景

创建 issue、提交或修改 PR 正文、发布重要状态评论后，先读一遍保存后的帖子，再请求评审、批准或合并。要看平台上实际保存并渲染出的那份，不只是本地草稿或实时预览；粘贴、保存后，显示的内容可能已经变了。

## 具体指导

在平台上重新打开保存后的帖子，按评审者的方式读一遍。确认标题正确显示、列表条目和缩进保留、换行与空行未丢失、复选框能正常显示、代码块仍有正确的起止标记、表格没有错列。检查是否因粘贴或编辑器删除换行而变成一整段。在平台编辑器里修复问题，保存后再次回读。确认保存后的显示完整，才请求评审。到此为止；帖子已经准确后，不必为风格反复修改。

## 反模式

Agent 在本地编辑器里写好长篇 PR 正文，粘贴进网页表单。粘贴把验收清单压成一行普通文字，还合并了两个标题。作者随即请求评审，两位评审者的理解却不同，其中一位把清单当作非正式说明。直到评审讨论中发生范围争议，误会才暴露出来。

## 原因

评审者和后来的读者依据的是保存后显示的帖子，不是草稿。排版损坏可能把要求藏起来：复选框变成普通文字，就不再标示清单项；标题变成正文，就更难找到对应小节。回读能检查发布后的帖子是否仍然正确呈现作者写下的内容。

## 例外与边界

已经核对过的帖子如果只改了一行，检查改动区域即可。有些平台允许在编辑视图中重读保存后渲染的内容，在那里检查也可以，但不能只看尚未保存的预览。这里只确认帖子是否正确保存和显示，不判断论证是否充分；内容方面可参考 issue 结构和 PR 正文的相关 Practice。

## 示例

提案 issue 提交后，作者重新打开它，发现验收清单显示成了三行连续文字，因为草稿中的连字符没有被平台转换。他把正文改成正确的复选框语法，保存后再读一遍，然后才在维护者频道里提及这个 issue。
