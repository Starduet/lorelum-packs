# 请求评审前先回读你发出的帖子

## 适用场景

issue 刚创建、PR 正文刚提交或编辑、重要状态评论刚发出，作者即将请求评审、批准或合并时使用。这里的决策是：保存后的帖子是否仍然表达草稿想表达的内容。本地草稿或实时预览窗口都不是保存后的帖子；只有平台上渲染出的那份才算。

## 具体指导

在平台上重新打开保存后的帖子，按评审者的方式读一遍。确认标题渲染成了标题、列表保留了条目和缩进、换行与空行幸存、checkbox 渲染成 checkbox、代码块保持围栏、表格保持列宽。检查有没有因为粘贴或编辑器剥离换行而被压扁成一整段。在平台编辑器里修复缺陷，保存后再次回读。一遍通过、渲染完好之后才请求评审。到此为止——帖子已经准确之后的反复风格化修改不属于这个决策。

## 反模式

Agent 在本地编辑器里写好长篇 PR 正文，粘贴进网页表单。粘贴把验收 checklist 压成一行散文、合并了两个标题。作者随即请求评审；两位评审者读到的内容不同——一位把 checklist 当作非正式说明——范围之争在评审串里爆发后才暴露这个误会。

## 原因

保存后渲染出的帖子才是评审者和后来者据以行动的产物，撰写时的保真度什么也证明不了。排版损坏会无声地改变语义：变成散文的 checkbox 不再是验收标准，变成正文的标题摧毁了扫读路径。回读一次就能闭合"写了什么"与"发布了什么"之间的缝隙。

## 例外与边界

对已验证帖子的一行编辑只需抽查编辑区域。作者当场重读可编辑源并就地渲染的平台，在该视图内完成回读也算满足——只要检查的是保存后的渲染。本条验证的是传输与渲染，不是论证质量——内容层面的检视属于 issue 结构与 PR 正文的各条 Practice。

## 示例

提案 issue 提交后，作者重新打开，发现验收 checklist 渲染成了三行连排——草稿用的连字符平台没有转换。他把正文改成规范的 checkbox 语法，保存，再回读一遍，然后才在维护者频道里提及这个 issue。
