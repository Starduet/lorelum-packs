# 用新提交回应反馈并在评审期间冻结

## 适用场景

开放中的 PR 收到评审反馈，或一轮正式评审正在该分支上进行，作者必须决定改动以何种方式到达分支、何时到达时使用。尚未邀请任何人评审的分支不适用本条。

## 具体指导

用"向分支追加提交"回应反馈，而不是重写评审者已经读过的历史；每个提交写明它处理哪条意见。评审要求的修复与无关改进分属不同提交，无关的更倾向另开 PR。仓库运行正式评审轮（自动化 pass、独立评审者、排期会话）时，在该轮结束前冻结分支上的代码变更：记录发现、把修复排进队列，而不是中途推上去。只有评审者提出要求或到达仓库定义的检查点时才 rebase 或 squash。当每条意见要么有对应提交、要么有说明原因的书面回复时停止。

## 反模式

双轮评审进行到一半，作者 force-push 了一份"清理过的"历史。第一轮的全部行内评论成了孤儿，指向已不存在的行；独立评审者从零重来，而被孤儿化的意见里有一条真实存在的竞态条件在重写中丢失。最终合并带着一个评审流程本来已经抓到的缺陷。

## 原因

评审证据锚定在评审者读过的提交状态上。新提交延伸这份记录，让每条意见可追溯到它的修复；重写摧毁这个映射，轮中变更使该轮结论失效——流程为其用不上的评审买了单。当多个独立轮必须对同一个冻结状态签字时，代价还会复利放大。

## 例外与边界

评审者可以在明确的时点显式要求 rebase 或 squash——那时才照做，不要提前。尚未开放评审的分支是私有历史，可以自由重写。评审轮运行期间必须落地的紧急修复走仓库声明的紧急路径，而不是沉默处理——并且重跑该轮，而不是让它在移动的靶子上继续。

## 示例

结构化评审的第一轮返回六条意见。作者以独立提交修复五条，提交标题形如
`fix: guard snapshot race (review r1-3)`，并在第六条下回复说明该建议为何会破坏一个已固定的行为。第二轮评审这个冻结的结果，每条意见要么被处理要么被回答，一次通过。
