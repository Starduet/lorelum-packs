# 用新提交回应反馈并在评审期间冻结

## 适用场景

邀请他人评审 PR 后，回应意见时不要改写他们已经读过的历史。正式评审或独立评审正在进行时，还要等这一轮结束后再改分支。尚未邀请任何人评审的分支，仍可自由重写历史。

## 具体指导

追加新提交来处理反馈，不要重写评审者已经读过的提交。每个提交说明它处理了哪条意见。评审要求的修复与无关改进分开提交，无关改进最好另开 PR。

正式评审正在进行时，无论是自动化审查、独立评审还是预定的评审会话，都保持分支代码不变，直到这一轮结束。先记录意见，把修复排到轮次结束后，不要中途推送。只有评审者要求，或到了仓库规定的时间点，才 rebase 或 squash。每条意见都要有处理结果：要么有对应的修复提交，要么书面解释为何不改。

## 反模式

双轮评审进行到一半，作者 force-push 了一份“清理过的”历史。第一轮的全部行内评论都指向了新历史中已不存在的行。独立评审者不得不重新开始，其中一条关于真实竞态条件的意见随原有上下文一起丢失。最终合并仍带着评审本已发现的缺陷。

## 原因

评审者依据某个具体提交提出意见。追加提交能保留该版本，并说明哪次修复处理了哪条意见。重写历史会移除这些引用；评审中途推送则可能让不同评审者针对不同版本得出结论。多轮独立评审若要比较结论，就需要针对同一个未变动的版本。

## 例外与边界

评审者可以明确要求在某个时间点 rebase 或 squash；到时再做，不要提前。尚未开放评审的分支是私有历史，可以自由重写。必须在评审期间合入的紧急修复，应按仓库声明的紧急流程处理，不能悄悄推送；修改后要重跑该轮评审，不能接着评审旧版本。

## 示例

结构化评审的第一轮返回六条意见。作者以独立提交修复五条，提交标题形如
`fix: guard snapshot race (review r1-3)`，并在第六条下回复说明该建议为何会破坏一个已固定的行为。第二轮评审这个冻结的结果，每条意见要么被处理要么被回答，一次通过。
