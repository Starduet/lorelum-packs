# 让渲染条件真正成为布尔值

## 适用场景

编写或审查 `{value && <Thing />}` 形态的条件渲染时应用。判断左操作数的假值域是只含 `false` 与 `undefined`，还是也包含 JSX 会渲染成内容的值。

## 具体指导

`&&` 在左操作数为假时原样返回它，而 JSX 会渲染数字——所以 `{count && <Badge />}` 在计数为零时会把文本 `0` 显示出来。条件的类型不是真布尔时，先把它化归为布尔：

```tsx
{error.code > 0 && <ErrorBanner code={error.code} />}
```

显式比较、`Boolean(...)`、带显式 `null` 分支的三元表达式都可以；决策点在于作者说清了零值情形的含义，而不是把它丢给隐式转换。空字符串和 `NaN` 遵循同一规则：`NaN` 会渲染成文本，空字符串会渲染出一个空文本节点，而 `null` 什么都不渲染。

不要一刀切禁用 `&&`：左操作数本就是布尔——旗标、比较、谓词调用——时，`{isOpen && <Panel />}` 是地道且正确的写法。可审查的问题只有「这个表达式会不会是一个会被渲染出来的假值」，它首先是类型问题，从来不是风格问题。

## 反模式

错误横幅用 `{error.code && <Banner ... />}` 守卫，而 `code` 在成功时为 `0`、失败时为非零码。每条成功路径都在表单旁边渲染出一个多余的 `0`——零是假值，但仍是一个 JSX 会显示的数字。

## 原因

JSX 会渲染交给它的任何子节点，而 `&&` 在左操作数为假时把它透传下去，数字和字符串于是泄漏进树里成为内容。把条件化归为真布尔，让「是否渲染」与「显示什么」彼此独立——零值情形渲染出「无」，而不是渲染出零。

## 例外与边界

- 真布尔条件无需改动；给 `bool` 套 `Boolean()` 是噪音。
- 零是有意义的展示值时，三元形式能把这层意图写明——本篇不是「零绝不能渲染」，而是「零的渲染必须是被选择的」。
- TypeScript 能收窄一部分：类型为 `boolean` 的左操作数不会泄漏数字；失效模式集中在无类型边界、API 响应和算术结果上。
- 本篇只管辖渲染条件；不涉及非 JSX 逻辑中的真值判断——那里 `if (items.length)` 可能完全清晰。

## 示例

搜索结果页头只在至少有一条结果时显示匹配数。比较运算让零值情形显式化；之前的 `resultCount && ...` 形态在结果集为空时会在标题下渲染出文本 `0`。

```tsx
function ResultsHeader({ resultCount }: { resultCount: number }) {
  return (
    <header>
      <h1>Results</h1>
      {resultCount > 0 && (
        <p>
          {resultCount} match{resultCount === 1 ? "" : "es"}
        </p>
      )}
    </header>
  );
}
```

空结果集现在只渲染标题。如果产品决定改显「0 matches」，三元形式就能表达——本篇的要点正是：零值情形的含义要出现在代码里，而不是从隐式转换里掉出来。
