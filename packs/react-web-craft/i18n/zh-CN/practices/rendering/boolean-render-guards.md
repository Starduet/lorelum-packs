# 让渲染条件真正成为布尔值

## 适用场景

编写或审查 `{value && <Thing />}` 时，检查 `value` 为假值的情况：React 收到的是 `false`
这样会被忽略的值，还是 `0` 这样会显示出来的数字？

## 具体指导

`&&` 在左操作数为假值时原样返回它，而 React 会显示数字。所以 `{count && <Badge />}`
在计数为零时会显示文本 `0`。条件不是布尔值时，先明确转换成布尔值：

```tsx
{error.code > 0 && <ErrorBanner code={error.code} />}
```

可以用显式比较、`Boolean(...)` 或带 `null` 分支的三元表达式，说明何时显示元素。`NaN`
和空字符串也应明确处理；尤其是 `NaN`，像 `0` 一样，作为假值左操作数被返回后仍会显示成文本。

左操作数已经是布尔值时，例如布尔标志、比较结果或谓词返回值，就保留 `&&`。`{isOpen && <Panel />}`
是常见且正确的写法。要检查的是：假值会不会意外显示出来，而不是要求统一成某种 JSX 风格。

## 反模式

错误横幅用 `{error.code && <Banner ... />}` 守卫，而 `code` 在成功时为
`0`、失败时为非零码。每条成功路径都在表单旁边渲染出一个多余的
`0`——零是假值，但仍是一个 JSX 会显示的数字。

## 原因

左操作数为假值时，`&&` 返回的是这个操作数，不一定是 `false`。React 会显示 `0` 和 `NaN`
这样的数字，但会忽略布尔子节点。使用布尔条件，就能把「是否显示元素」与「显示什么值」分开。

## 例外与边界

- 真布尔条件无需改动；给 `bool` 套 `Boolean()` 是噪音。
- 如果零本来就是需要显示的值，用三元表达式明确写出这种情况；这里防的是意外显示零，并不禁止显示零。
- TypeScript 能排除部分情况：类型为 `boolean`
  的左操作数不会把数字传给 React；仍需留意无类型边界、API 响应和算术结果。
- 这里讨论的只是渲染条件，不是非 JSX 逻辑中的真值判断；例如 `if (items.length)` 可能已经很清楚。

## 示例

搜索结果页头只在至少有一条结果时显示匹配数。比较运算让零值情形显式化；之前的 `resultCount && ...`
形态在结果集为空时会在标题下渲染出文本 `0`。

```tsx
function ResultsHeader({ resultCount }: { resultCount: number }) {
  return (
    <header>
      <h1>Results</h1>
      {resultCount > 0 && (
        <p>
          {resultCount} match{resultCount === 1 ? "" : "es"}
        </p>
      )}
    </header>
  );
}
```

空结果集现在只渲染标题。如果产品决定改显「0
matches」，三元形式就能表达——本篇的要点正是：零值情形的含义要出现在代码里，而不是从隐式转换里掉出来。
