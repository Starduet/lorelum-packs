# 按审查意见改代码前先确认它成立

## 适用场景

评审者、另一个 Agent 或分析工具指出了问题，准备按它修改代码、测试、文档或计划之前，先确认这条意见对当前需求和文件是否成立。缺陷已经复现，就直接处理。如果只是引用的证据可能过时，就检查证据是否仍适用。

## 具体指导

1. 对照当前请求或规格：需求确实要求这样改，还是改了反而会与需求冲突？
2. 检查当前分支上的文件，评审引用的可能是旧 diff。
3. 记录问题是已确认、尚未确认，还是需要有权修改需求的人作决定。
4. 已确认的局部问题就修复；未确认就补证据；需要改变要求就回到需求讨论。

问题尚未确认，或改动会改变已接受的行为时，不要动手编辑。

## 反模式

评审者建议移除键盘导航，因为聚焦的指针测试通过、事件处理代码看起来复杂。删掉它能简化组件、保持可见测试全绿，但已接受的无障碍需求明确包含键盘使用。这个貌似合理的简化与该需求冲突。

## 原因

发现是一个主张，不是事实。核实它既保留有用的评审输入，又不让自信、过期上下文或"代码越小越好"的偏好凌驾于任务之上。

## 例外与边界

延迟会扩大伤害时，先立即遏制可利用的安全问题或破坏性故障；要长期保留这项措施之前，再核实。维护者决定改变范围，属于新的授权，不是技术问题的发现。

## 示例

评审说某个缓存键忽略了 locale、可能返回错误语言的文本。Agent 检查当前分支，发现 locale 在后来的重构中已加入；该发现引用的是旧 diff。它把发现标记为"对当前产物未确认"，不做任何代码改动。
