# 提交前删掉没有必要的改动

## 适用场景

完整的 diff 已能整体评判、恰在提交或交接之前使用。它检查整个 diff 的必要性；不重新选择最初的设计，也不处理未经验证的评审发现。

## 具体指导

1. 把完整 diff 通读一遍，列出实质新增：文件、抽象、兜底、接口、I/O、测试和文档。
2. 为每个新增点名支撑它的需求、风险、契约或依赖。删掉没有当前理由的新增，合并重复，复用合适的既有代码。
3. 保留必需行为、迁移支持和防护；当前契约或发布流程需要的迁移、兼容、安全、审计或回退代码要保留。
4. 删除会改变行为时，提交前验证修改后的状态：沿 diff 触及的某条路径，跟踪一个代表值和一个失败。
5. 质疑重复的解析、规范化、鉴权、catch 后默认的包装和嵌套重试——每个都需要不同的条件和归属——并检查是否有共享守卫不必要地阻塞状态查询、停止、升级或修复。
6. 删除共享守卫、鉴权、迁移或恢复保护之前，先枚举其当前调用方和入口，并对每个不同的信任边界各验证一条路径（见"在真正负责该事实的边界做校验"）；其他入口依赖的检查，单条代表路径不够。

追踪只限被改的行为；减法评审不是审计整个仓库的邀请。以"仍满足请求及其风险的最小 diff"结束。

## 反模式

终审时，上游路由守卫让服务层鉴权检查显得多余，恢复标记又没有正常路径的读取方。为了缩小 diff，Agent 把两者都删了，却保留了一个熟悉的包装器和重复解析器。聚焦的路由测试依旧全绿，但另一个调用方可以直接到达服务，被中断的工作再也无法恢复。

## 原因

局部合理的新增放在一起更容易评判。减法评审移除没有支撑的维护成本，同时不把"最小"当作正确性。

## 例外与边界

改变已接受的架构或公共契约之前，先询问负责的权威。

## 示例

任务为仓库新增分块图片上传，而仓库已有媒体类型校验器。提交前，Agent 删掉未使用的进度抽象和重复的媒体类型 helper，复用既有校验器，并保留上传契约要求的分块大小上限和部分文件清理。删除后重跑受影响的上传检查。
