# 提交前删掉没有必要的改动

## 适用场景

实现已经完成、准备提交或交接时，通读整个 diff，看看每项新增是否确实为任务所需。这次最终检查不代替最初的设计选择，也不代替核实评审意见是否成立。

## 具体指导

1. 把完整 diff 通读一遍，列出实质新增：文件、抽象、兜底、接口、I/O、测试和文档。
2. 说明每项新增是为了哪条需求、风险、契约或依赖。现在没有理由保留的就删掉，重复的合并，能用合适的既有代码就复用。
3. 保留必需行为、迁移支持和防护；当前契约或发布流程需要的迁移、兼容、安全、审计或回退代码要保留。
4. 删除会改变行为时，在提交前验证修改后的状态：选一条 diff 触及的路径，沿各层跟踪一个代表性输入值，再跟踪一次失败的处理过程。
5. 仔细看重复解析、规范化、鉴权、catch 后返回默认值的包装，以及嵌套重试。每一处都应有各自可能发生的情况和负责的组件。还要检查共享守卫是否无端阻塞状态查询、停止、升级或修复。
6. 删除共享守卫、鉴权、迁移或恢复保护之前，列出当前调用方和入口，对每个不同的信任边界各验证一条路径（见"在真正负责该事实的边界做校验"）。其他入口也依赖这项检查时，只验证一条代表路径不够。

只跟踪本次改变的行为，不必借此审计整个仓库。保留满足请求、应对相关风险所需的最小 diff，就可以结束。

## 反模式

终审时，上游路由守卫让服务层鉴权检查显得多余，恢复标记又没有正常路径的读取方。为了缩小 diff，Agent 把两者都删了，却保留了一个熟悉的包装器和重复解析器。聚焦的路由测试依旧全绿，但另一个调用方可以直接到达服务，被中断的工作再也无法恢复。

## 原因

只看一个文件时显得合理的新增，放到整个改动里看，可能并不需要。删掉这类维护负担，但不要把 diff 更小当成正确。

## 例外与边界

改变已接受的架构或公共契约之前，先询问有权决定该变更的负责人。

## 示例

任务为仓库新增分块图片上传，而仓库已有媒体类型校验器。提交前，Agent 删掉未使用的进度抽象和重复的媒体类型 helper，复用既有校验器，并保留上传契约要求的分块大小上限和部分文件清理。删除后重跑受影响的上传检查。
