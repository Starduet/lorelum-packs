# 给被委派的 Agent 足够的决策上下文

## 适用场景

委派的工作需要接收方做出与委派方相同的范围或质量判断之前使用。决定性信息存在于对话、早前评审或接收方不会想到去查的多份来源时使用。输入输出完全明确的机械任务是近失场景，只需那些说明。

## 具体指导

1. 说明请求的结果，以及管辖它的用户请求或规格。
2. 列出接收方无法从任务名推断的仓库事实：相关状态、必需约束、非目标，以及塑造工作的已接受和被拒绝决策。当接收方可能重蹈那个"局部合理"的选择时，一并给出拒绝理由。
3. 定义委派边界：范围内的文件或符号、要返回的结果、接收方负责的检查，以及哪些发现需要上报。
4. 链接大型来源，而不是复制其全部内容。

当接收方能说清"它必须决定什么、必须保留什么、不能悄悄重新解释什么"时停止。

## 反模式

用户和主 Agent 商定 Pack 示例必须展示有能力的 Agent 真实会犯的错误，并明确拒绝一个调度器示例为混乱且造作。主 Agent 随后只用一句"读编写计划并改进需求类 Practice"来委派重写。计划提到真实感，却没提被拒的示例及其失败原因。被委派的 Agent 打磨了调度器措辞、返回了 schema 合法的文件，重复了用户已推翻的决策。

## 原因

委派为省时省上下文而移除了对话历史，但判断力依赖的不只是任务名。一份聚焦决策的资料包保留"区分可接受结果与貌似合理的错误结果"的那些理由，又不让每个 Agent 重放完整的父任务。

## 例外与边界

不要为重命名、精确替换或选择已封闭的机械任务制造长简报。不要把整段转录、原始日志、机密或无关探索贴进资料包；过量的上下文会淹没资料包要保留的那些决策。接收方仍要验证当前文件和证据，而不是把资料包当作"仓库没变"的证明。

## 示例

委派 CLI 安装器改动前，主 Agent 写道："默认安装必须使用官方 registry，显式自定义仓库也必须可用。复用既有 Pack 校验器和物化器。不要添加任意 URL 来源、自动镜像回退、鉴权插件系统或新缓存。保留当前输入预算和类型化错误。返回改动文件、聚焦测试，以及你认为不可避免的契约变更。"接收方有足够上下文保住必需的扩展性，而不发明通用来源平台。
