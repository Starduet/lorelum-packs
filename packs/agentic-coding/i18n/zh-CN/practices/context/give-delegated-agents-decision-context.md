# 给被委派的 Agent 足够的决策上下文

## 适用场景

准备把工作交给另一个 Agent，但它需要的决定有些只存在于你的对话或早前评审中时，先把这些依据交代清楚，再让它判断范围或质量。它不会想到去查的来源中如果也有决定性信息，一并提供。输入输出已完全确定的机械任务，只需给操作说明，不必另写简报。

## 具体指导

1. 说明需要什么结果，以及以哪份用户请求或规格为准。
2. 交代任务名本身看不出的仓库事实：相关现状、必需约束、不做什么，以及已经接受或否决的决定。被否决的做法如果对接收方仍显得合理，就一并解释为什么不能这样做。
3. 明确允许修改的文件或符号、要交回的结果、接收方负责的检查，以及哪些新发现必须向你说明。
4. 大型来源给链接，不要全文复制。

接收方能说清需要自己决定什么、必须保留什么、哪些要求不能擅自改解，就可以委派。

## 反模式

用户和主 Agent 商定 Pack 示例必须展示有能力的 Agent 真实会犯的错误，并明确拒绝一个调度器示例为混乱且造作。主 Agent 随后只用一句"读编写计划并改进需求类 Practice"来委派重写。计划提到真实感，却没提被拒的示例及其失败原因。被委派的 Agent 打磨了调度器措辞、返回了 schema 合法的文件，重复了用户已推翻的决策。

## 原因

另一个 Agent 通常看不到你的对话历史。不知道早前决定的理由，它即使认真工作，也可能再次采用用户已否决的做法。把这些理由交代清楚，不必让它重读整个主任务。

## 例外与边界

重命名、精确替换等选择已经确定的机械任务，不必写长简报。不要粘贴整段对话、原始日志、机密或无关调查；信息过多反而会淹没重要决定。接收方仍须核对当前文件和证据，不能把简报当作仓库未变的证明。

## 示例

委派 CLI 安装器改动前，主 Agent 写道："默认安装必须使用官方 registry，显式自定义仓库也必须可用。复用既有 Pack 校验器和物化器。不要添加任意 URL 来源、自动镜像回退、鉴权插件系统或新缓存。保留当前输入预算和类型化错误。返回改动文件、聚焦测试，以及你认为不可避免的契约变更。"接收方有足够上下文保住必需的扩展性，而不发明通用来源平台。
