# 上下文丢失后先重新落地

## 适用场景

同一任务或 Agent 在压缩、中断或长暂停之后恢复、只剩摘要或部分记忆时使用。在编辑、扩张计划或汇报进度之前做。已知暂停之前，应改为写检查点。结论来自另一个 Agent 或贡献者时，验证那次交接，而不是用这条同会话恢复规则。

## 具体指导

1. 只把摘要当作寻找原始材料的索引；其中任何结论都不当作事实。
2. 重新打开当前用户请求、已接受 issue 或规格、相关计划和决策、当前分支与 diff、已记录的测试或评审结果。
3. 逐条核对下一步行动所依赖的摘要断言。
4. 写下当前目标、允许的改动、第一个仍缺失的必需行为、哪些结果仍适用于当前文件、下一个有理由的行动；削减缺乏证明的完成表述。

当这些事实清楚时停止；更小的集合能回答下一个决策时，不要通读整个项目。

## 反模式

用户要求从真实远端仓库安装。压缩后，摘要说"安装已完成，只剩清理"。仓库单元测试是绿的，开始重构感觉像有用的进展。重新打开已接受 issue 和当前 diff 发现：只测过假传输，真实远端路径从未运行。摘要把部分实现变成了完成。

## 原因

摘要保持连续性，但可能遗漏最要紧的需求、文件变更或失败检查。重开这些具体来源，防止一个遗漏变成更多工作或不实进度报告的依据。

## 例外与边界

只有一个产出的琐碎任务可能只需与当前文件快速比对。早前结果测试的文件和条件相同时可继续使用。用户请求、已接受 issue 和规格冲突时，停下来问哪个管辖工作，而不是选与摘要一致的那个。来自其他 Agent 的主张需要交接验证。

## 示例

用户要求解析器拒绝坏 token 并在截断声明后恢复。恢复重构后，Agent 重开该需求、当前 diff 和已记录结果：合法语法和坏 token 拒绝在当前 commit 通过，但没有测试截断过声明。Agent 报告"核心解析已验证；截断输入恢复未检查"，接下来补跑缺失场景，而不是开始清理。
