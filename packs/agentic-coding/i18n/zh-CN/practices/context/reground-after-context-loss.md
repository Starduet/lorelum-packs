# 上下文丢失后重新核对原始来源

## 适用场景

压缩上下文、中断或长时间暂停后，回到同一任务，却只剩摘要或零散记忆时，先核对原始来源，再编辑、扩大计划或汇报进度。如果暂停还没发生，应先写检查点。如果结论来自另一个 Agent 或贡献者，应验证交接，不能当作自己在同一会话中恢复工作。

## 具体指导

1. 用摘要查找原始材料，不把其中的结论直接当作事实。
2. 重新打开当前用户请求、已接受 issue 或规格、相关计划和决定、当前分支与 diff，以及记录下来的测试或评审结果。
3. 下一步依赖摘要中的哪条说法，就用这些来源逐条核对。
4. 写清当前目标、允许改什么、第一个仍缺失的必需行为、哪些结果仍适用于当前文件，以及接下来应做什么。完成情况说得超过证据所能证明的，就改正。

这些事实弄清就够了。几份材料已能回答下一步的问题，就不必通读整个项目。

## 反模式

用户要求从真实远端仓库安装。压缩后，摘要说"安装已完成，只剩清理"。仓库单元测试是绿的，开始重构感觉像有用的进展。重新打开已接受 issue 和当前 diff 发现：只测过假传输，真实远端路径从未运行。摘要把部分实现变成了完成。

## 原因

摘要保持连续性，但可能遗漏最要紧的需求、文件变更或失败检查。重开这些具体来源，防止一个遗漏变成更多工作或不实进度报告的依据。

## 例外与边界

只有一个产出的简单任务，可能只需快速对照当前文件。早前结果检查的是同样的文件和条件，就可以继续使用。用户请求、已接受 issue 和规格冲突时，先问应以哪份为准，不要选择与摘要一致的那份。其他 Agent 提供的结论仍要经过交接验证。

## 示例

用户要求解析器拒绝坏 token 并在截断声明后恢复。恢复重构后，Agent 重开该需求、当前 diff 和已记录结果：合法语法和坏 token 拒绝在当前 commit 通过，但没有测试截断过声明。Agent 报告"核心解析已验证；截断输入恢复未检查"，接下来补跑缺失场景，而不是开始清理。
