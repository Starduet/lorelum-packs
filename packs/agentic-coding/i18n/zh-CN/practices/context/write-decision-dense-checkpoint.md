# 写下能保住决策的检查点

## 适用场景

已知的上下文压缩、长时间暂停或会话边界之前、后续工作需要一段简短恢复记录时使用。决定哪些事实必须活过边界。在压缩或中断之前，把检查点存到恢复任务读得到的地方。上下文已经丢失后，不要凭记忆重建检查点；改为重新打开请求、文件和结果。

## 具体指导

1. 记录管辖来源：当前用户目标，以及管辖工作的确切请求、已接受 issue、规格或计划。
2. 记录已接受的决策及其对下一步的限制；把被拒方案压缩为"不得重复的理由"。
3. 记录第一个未完成的必需行为、仍然适用的测试或评审结果（含其检查的 commit 或文件），以及仍然存在的风险、阻塞和未确认假设。
4. 记录下一个有理由的行动；链接到被改文件和完整日志，而不是复制它们。

当冷读者能说出"该重开什么、什么已完成、什么没有、什么不能假设、从哪里继续"而无须重放对话时停止。

## 反模式

用户只要求诊断一个鉴权失败。临近上下文上限，Agent 把最近的命令输出、改过的文件名和一个看起来有希望的缓存修复抄进检查点，因为这些细节好收集、显得具体。它漏掉了"尚未授权实现""拒绝路径仍未验证""缓存解释只是假设"。恢复的会话很可能直接开始实现那个猜测。

## 原因

恢复的会话需要的是"什么管辖工作、还剩什么"的简短记录，而不是近期活动的摘要。让请求、已接受决策、缺失行为和限制保持可见，防止最近的日志或诱人假设操纵下一步。完整证据可以通过链接保留。

## 例外与边界

事故响应、审计、法务或可复现性要求留存完整日志时，单独保留；检查点应链接而非替代那份证据。极短的无状态任务可能只需一句话。检查点不授权新 Agent 不经验证就信任另一个 Agent 的结论——那是交接边界。

## 示例

用户要求一次不丢既有行的存储迁移。压缩之前，Agent 记录已接受的迁移文档、"回退被证明之前保留旧读取器"的决策、当前已改文件，以及"前向迁移在当前 commit 通过"的结果。它明确写"带数据的回退尚未运行"，链接完整输出，并记录两个废弃方案为何过早改写行。下一个行动是带数据回退检查，不是实现清理。
