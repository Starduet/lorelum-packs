# 写下能保住决策的检查点

## 适用场景

已知接下来要压缩上下文、长时间暂停或切换会话，而且任务之后还要继续，就在中断前留一份简短记录，存到恢复工作时能读到的地方。先想清后续需要哪些事实。上下文已经丢失，就不要凭记忆补写检查点，应重新打开请求、文件和结果。

## 具体指导

1. 记录当前用户目标，以及具体以哪份请求、已接受 issue、规格或计划为准。
2. 记录已接受的决定，以及它们怎样限制下一步。被否决的方案只留下不能再采用的理由，不必重述讨论。
3. 记录第一个仍未完成的必需行为、仍然适用的测试或评审结果及其检查的 commit 或文件，还有未解决的风险、阻塞和未确认假设。
4. 写清下一步该做什么、为什么。改动文件和完整日志给链接，不要全文复制。

没有读过对话的人，能看出应重开什么、哪些已完成、哪些没完成、什么不能假设、从哪里继续，就足够了。

## 反模式

用户只要求诊断一个鉴权失败。临近上下文上限，Agent 把最近的命令输出、改过的文件名和一个看起来有希望的缓存修复抄进检查点，因为这些细节好收集、显得具体。它漏掉了"尚未授权实现""拒绝路径仍未验证""缓存解释只是假设"。恢复的会话很可能直接开始实现那个猜测。

## 原因

恢复后的会话需要简短记录哪些要求决定当前工作、还有什么未完成，而不是近期活动摘要。保留请求、已接受决策、缺失行为和证据限制，才能防止最近的日志或诱人假设左右下一步。完整证据可以通过链接保留。

## 例外与边界

上下文即将耗尽时若正在处理进行中的事故或安全遏制，先写最小恢复记录——当前动作、负责人、遏制或回退状态、下一步——立即执行遏制，待事故稳定后再补完整检查点。事故响应、审计、法务或可复现性要求留存完整日志时，单独保留；检查点应链接而非替代那份证据。极短的无状态任务可能只需一句话。检查点不授权新 Agent 不经验证就信任另一个 Agent 的结论——那是交接边界。

## 示例

用户要求一次不丢既有行的存储迁移。压缩之前，Agent 记录已接受的迁移文档、"回退被证明之前保留旧读取器"的决策、当前已改文件，以及"前向迁移在当前 commit 通过"的结果。它明确写"带数据的回退尚未运行"，链接完整输出，并记录两个废弃方案为何过早改写行。下一个行动是带数据回退检查，不是实现清理。
