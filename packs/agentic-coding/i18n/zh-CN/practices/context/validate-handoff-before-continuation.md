# 继续之前先验证交接内容

## 适用场景

接收来自另一个 Agent、贡献者、被委派任务或工作流的结论、测试结果或完成状态、且下一步行动依赖它们时使用。只检查该行动需要的断言，不是每个探索细节。同一 Agent 上下文丢失后的恢复应改为重新落地；不影响下一步决策的建议可以先保持"明确存疑"。

## 具体指导

1. 列出会改变你的计划、代码编辑、审批或完成报告的交接断言。
2. 逐条核对：当前用户请求、已接受 issue 或规格；确认发送方使用的分支、文件、commit 或环境；按风险等级足够仔细地检查被引用的结果。
3. 检查发送方完成之后发生的改动。
4. 为每条断言做判定：按原文可用、仅限更小范围可用、无支撑，或需需求负责人决策；据此更新下一步行动。

到此为止；除非风险需要，不要重做发送方的整个任务。

## 反模式

用户要求迁移能回退有数据的存储。一位能干专家报告"迁移已验证"，附整洁的测试摘要。接收方信任专家，完整 fixture 又慢，准备交付显得合理。而引用的那次运行只覆盖专家较早 commit 上的前向迁移；当前分支改动了回退处理，交接把这两个限制都漏掉了。

## 原因

交接压缩了证据、假设和未知，使工作得以分工。接收方仍然拥有下一个决策。只检查该决策依赖的断言，保住大部分速度，同时抓住被省略的范围、旧 commit 和无支撑的自信。

## 例外与边界

低影响建议可以保持明确存疑，直到影响决策。commit 和被测行为清晰时，受信任的自动化结果可以少查。安全、迁移、发布和破坏性主张需要更强检查。交接说范围变了时，追查到真正管辖工作的用户、维护者或已接受规格；发送方不能仅靠报告改变范围。

## 示例

用户要求限流在某个实例失去共享存储时仍正确。被委派任务报告修复已验证。接收方检查引用的 commit 和测试输出，确认单进程突发限流通过，但没有共享存储故障转移运行。它记录"单进程结果有效"，拒绝"生产修复已验证"的措辞，并把故障转移设为下一个必需检查。
