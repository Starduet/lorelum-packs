# 继续之前先验证交接内容

## 适用场景

另一个 Agent、贡献者、被委派任务或并行工作报告了结论、测试结果或完成状态，而你下一步要依赖这些信息时，先核对。只查下一步需要的说法，不必查每项探索细节。如果是在上下文丢失后恢复自己的工作，应重新核对原始来源。不影响下一步决定的建议，可以明确保留为尚未验证的建议。

## 具体指导

1. 列出交接中哪些说法会影响你的计划、修改、审批或完成报告。
2. 逐条对照当前用户请求、已接受 issue 或规格，确认发送方用的是哪个分支、文件、commit 或环境，并按风险需要仔细查看引用的结果。
3. 检查发送方完成后又改了什么。
4. 分清每条说法是可以原样采用、只在更小范围内成立、没有依据，还是需要需求负责人决定，再据此调整下一步。

查到这里即可。除非风险确有需要，不必重做发送方的整个任务。

## 反模式

用户要求迁移能回退有数据的存储。一位能干专家报告"迁移已验证"，附整洁的测试摘要。接收方信任专家，完整 fixture 又慢，准备交付显得合理。而引用的那次运行只覆盖专家较早 commit 上的前向迁移；当前分支改动了回退处理，交接把这两个限制都漏掉了。

## 原因

交接概述证据、假设和未知，使工作得以分工。接收方仍要对下一步决定负责。只检查该决定依赖的说法，既保留大部分效率，也能发现被省略的范围、旧 commit 和缺乏依据的结论。

## 例外与边界

低影响建议可以明确标为暂未验证，直到它影响决策。commit 和被测行为清晰时，受信任的自动化结果可以少查。安全、迁移、发布和破坏性主张需要更强检查。交接说范围变了时，追查到真正决定工作要求的用户、维护者或已接受规格；发送方不能仅靠报告改变范围。

## 示例

用户要求限流在某个实例失去共享存储时仍正确。被委派任务报告修复已验证。接收方检查引用的 commit 和测试输出，确认单进程突发限流通过，但没有共享存储故障转移运行。它记录"单进程结果有效"，拒绝"生产修复已验证"的措辞，并把故障转移设为下一个必需检查。
