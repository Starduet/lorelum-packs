# 多份来源冲突时先确认听谁的

## 适用场景

当两份及以上已经相关的来源指向不同的预期行为、而下一个决策需要唯一基线时使用：当前请求、适用的仓库指令、已采纳的规格或生效契约、注明状态的决策记录、README、计划、代码与测试、历史或会话摘要。不要主动在仓库里搜索可能存在的分歧。如果已知来源已经一致、悬而未决的只是现有代码能否复用，应改为检查实现。

## 具体指导

1. 把有争议的行为隔离成一句话，例如订单记录保留多久。
2. 依据声明地位而不是文件类型说明每份已知来源的角色：定义当前行为、记录已接受的约束、提议未来工作、保留历史，或只是展示当前产物。已采纳的规格或生效契约起管辖作用——包括仓库明确采纳为契约的 README；未获采纳的 README 或通过的测试只说明今天存在什么；计划或原型描述的是未必被接受的工作。
3. 依据地位而不是细节、新旧或实现难易来决定哪个来源胜出：使用仓库声明的权威规则、明确的采纳或废止记录、以及经授权的纠正。
4. 记录管辖来源以及其他来源各自还能证明什么，让评审者能复现这个决定。

如果没有任何规则能解决实质性冲突——套件断言一种行为、决策记录说另一种、维护者评论与两者都不同——在编码前询问用户或负责的维护者。当有一份点名的来源定义了争议行为、其余来源都标注了角色时停止。

## 反模式

已采纳的策略要求审计记录保留七年，而一个较早的清理任务及其通过的测试一年后就删除它们。因为清理任务已在运行、测试也是绿的，保留它看起来比重启决策更安全。通过的测试只展示一个既存产物，不能压过关于预期保留期限的已采纳策略。

## 原因

各来源承担不同角色。把权威与提议、导航、历史、观察区分开，可以防止一个顺手可用的既存产物或一段详尽解释在未经批准的情况下变成目标。

## 例外与边界

当治理策略明确授权时，安全或数据保护规则可以覆盖产品指令。本地仓库指令只有在明确说明其范围和与继承规则的关系时才能改变继承规则；仅靠目录位置相近不构成覆盖。记录任何覆盖的范围。本 Practice 选择哪份来源定义意图，不选择实现设计，也不是一份大而全的仓库阅读计划。

## 示例

已接受的迁移计划说既有客户标识符必须保持稳定，而当前原型及其测试生成替换标识符，原型的 README 与测试一致。Agent 必须决定跟随哪份文档。它记录：已接受的计划是管辖来源，原型及其测试是未完成状态；除非另行批准，不保留替换标识符行为。
