# 多份要求冲突时先确认听谁的

## 适用场景

已知且相关的用户要求、适用的 repository
instruction、当前合同、带状态的决策记录、README 或目录导航、计划、代码与测试、历史资料或会话摘要中，有两份以上对目标行为说法不同，而下一步必须选一个基准时使用。不要为了寻找可能的冲突而扫描仓库。若已知来源没有冲突，问题只是能否复用现有实现，应去检查代码。

## 具体指导

先只看冲突的那项行为。逐份说明：它是在规定当前应当怎样、解释已接受的架构约束、提出未来工作、保留历史，还是只展示当前产物。依据仓库声明的 authority 规则、明确的采纳或 supersession 状态和有权人员的纠正，确定哪一份控制当前工作；更新更晚或写得更细都不能单独决定。README 或目录导航可以帮助定位材料，却不会因为写得详细就产生合同；代码和测试通常展示现状；计划或 Proposed 决策可能描述尚未接受的工作。记录最终听谁的，以及其他来源仍能证明什么。若规则无法裁定重大选择，编码前询问用户或负责人。

## 反模式

README 和当前测试都描述批量退款接口，当前 API 合同却没有它，Proposed 计划把它安排在后续阶段。接口已经有一个方便的 handler，保留它看起来比重开决定更稳妥；但代码和 README 只能说明已有产物，不能把提议中的工作升级为当前合同。

## 原因

不同来源承担不同角色。把 authority、提议、导航、历史和观察分开，能避免方便的现有产物或详细解释未经批准就被误当成目标。

## 例外与边界

如果治理规则明确规定安全或数据保护要求优先，它可以覆盖普通产品指令，但要记录覆盖范围。局部 repository
instruction 只有在作用域及其与继承规则的关系明确时，才能改变上层规则；目录更近本身不是覆盖依据。本条 Practice 只决定意图由谁定义，不选择实现方案，也不要求制订广泛的仓库阅读计划。

## 示例

已接受的迁移计划要求保留现有客户 ID，当前原型和测试却会生成新 ID。Agent 记录已接受的迁移计划决定目标，原型只是尚未完成的现状；除非另获批准，不会为了寻找更多实现而打开无关迁移模块，也不会因为已有测试更便宜就保留换 ID 的行为。
