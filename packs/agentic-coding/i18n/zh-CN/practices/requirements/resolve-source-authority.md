# 多份来源冲突时先确认听谁的

## 适用场景

请求说一种做法，规格、README、计划或测试却说另一种。决定实现哪种行为之前，先确认应以谁为准。相关依据也可能来自仓库指令、生效契约、决策记录、代码、历史或会话摘要。只处理已经发现的分歧，不要主动搜遍仓库找冲突。已知来源一致、只是想知道现有代码能否复用时，直接检查实现。

## 具体指导

1. 用一句话说清争议，例如订单记录究竟应保留多久。
2. 阅读各来源声明的状态，确认它是在规定当前行为、记录已接受的约束、提议后续工作、保留历史，还是只展示代码现状。文件类型本身不能决定优先级。应遵循已采纳的规格或生效契约，包括被仓库明确采纳为契约的 README。未获采纳的 README 和通过的测试只说明当前实现；计划或原型中的工作未必已经获准。
3. 按仓库的优先级规则、明确的采纳或替代记录，以及经授权的纠正来解决分歧。更详细、更新或更容易实现，都不是优先采用某份来源的理由。
4. 记录最终以哪份来源为准、其他来源仍能说明什么，让评审者能追溯这个决定。

如果这些规则仍不能解决重要分歧，例如测试、决策记录和维护者评论各说各话，编码前询问用户或负责的维护者。明确哪份来源决定争议行为，并交代其余来源的作用后，就可以继续。

## 反模式

已采纳的策略要求审计记录保留七年，而一个较早的清理任务及其通过的测试一年后就删除它们。因为清理任务已在运行、测试也是绿的，保留它看起来比重启决策更安全。通过的测试只展示一个既存产物，不能压过关于预期保留期限的已采纳策略。

## 原因

提案、历史记录和测试不一定在说明产品现在应该怎样工作。先确认它们的状态，才能避免把顺手的实现或详尽的说明当成未经批准的新需求。

## 例外与边界

当治理策略明确授权时，安全或数据保护规则可以覆盖产品指令。本地仓库指令只有在明确说明其范围和与继承规则的关系时才能改变继承规则；仅靠目录位置相近不构成覆盖。记录任何覆盖的范围。本 Practice 选择哪份来源定义意图，不选择实现设计，也不是一份大而全的仓库阅读计划。

## 示例

已接受的迁移计划要求既有客户标识符保持不变，而当前原型及其测试会生成新标识符，原型的 README 也这么写。Agent 记录以已接受的计划为准，原型和测试只是尚未完成的实现；除非另行批准，不保留替换标识符的行为。
