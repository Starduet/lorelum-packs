# 同时写清完成条件和不做什么

## 适用场景

当结果句已达成一致、且还没开始选择实现工作时使用。既要写明哪些行为必须成立，也要写清最合理的相邻工作中哪些不是必需的。如果请求的结果本身仍不清楚，先定义用户目标。

## 具体指导

1. 写一份调用方能观察到的行为的"完成当"清单，例如"无覆盖参数的安装解析官方 registry；带显式仓库的安装使用该自定义 registry"。这些就是宣布任务完成前必须通过的检查。
2. 写一份"不属于本任务"清单，列出能干的工程师可能顺手添加的诱人相邻功能——镜像、缓存、插件系统、通用定位器——并逐项明确排除在任务之外。
3. 区分调用方必须分辨的结果：不可用不等于空、被拒绝不等于已保存、过期不等于最新。把缺失的区分补进完成清单。
4. 用请求核对两份清单：即使删掉会缩小 diff 也要保留必需行为；即使能让设计更通用也要排除可选基础设施。
5. 当实际调用方和部署约束会改变验收时，先弄清它们；不要悄悄给不需要公开、敌意、多租户或永久离线场景的任务加上这些前提。

当两份清单足以让评审者区分"完成的工作""缺失的行为"和"范围扩张"时停止。

## 反模式

安装器需要默认官方 registry 和一个显式仓库 registry。因为 Git 获取代码本来就要改，通用定位器层、自动镜像回退、缓存和鉴权挂钩看起来都是高效的未来铺垫。后来的清理犯了相反的错误：为了缩小补丁删掉了自定义 registry 支持。两种选择都在优化实现的形状，而不是要求的安装行为。

## 原因

没有明确的行为边界，"更可复用"和"更小 diff"都会显得像质量。完成条件保护必需能力；非目标阻止有吸引力的平台工作变成当前承诺。

## 例外与边界

受支持输入、治理策略或已接受契约要求的检查，即使没有逐项列出也属于完成的一部分。说明这个依据，而不是把"健壮性"或"安全性"当作无限例外。后来经授权的需求可以新增非目标，但仅凭未来可能性不行。

## 示例

在构建新加载器时，Agent 很想加上镜像、缓存和一套插件系统。它写下："完成当：无覆盖参数的安装解析官方 registry；带显式仓库的安装使用该自定义 registry。"又写下："不属于本任务：自动镜像回退、鉴权插件、多 registry 聚合、通用文件或 HTTP 定位器、registry 缓存。"验证必须覆盖两条必需路径；不需要实现或永久禁止那些非目标。
