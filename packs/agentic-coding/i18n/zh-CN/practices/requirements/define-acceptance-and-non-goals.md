# 同时写清完成条件和不做什么

## 适用场景

用户要的结果已经说清，但还没决定具体改什么时，先写下做完后必须能用的行为，以及哪些看起来值得顺手做的功能不在本次范围内。结果本身还不清楚，就先确认用户目标。

## 具体指导

1. 写一份调用方可观察的完成条件清单，例如"不指定覆盖参数时，安装使用官方 registry；显式指定仓库时，安装使用该自定义 registry"。这些就是宣布任务完成前必须通过的检查。
2. 写一份“不属于本任务”清单。镜像、缓存、插件系统、通用定位器等功能，工程师很可能想顺手添加；把这类合理但非必需的扩展逐项排除。
3. 区分调用方必须分辨的结果：不可用不等于空、被拒绝不等于已保存、过期不等于最新。把缺失的区分补进完成清单。
4. 用请求核对两份清单：即使删掉会缩小 diff 也要保留必需行为；即使能让设计更通用也要排除可选基础设施。
5. 当实际调用方和部署约束会改变验收时，先弄清它们；不要擅自假设任务需要面向公众、防范恶意调用方、支持多租户或始终离线运行。

两份清单能让评审者看出哪些已完成、哪些必需行为还缺失、哪些属于额外扩展，就足够了。

## 反模式

安装器需要默认官方 registry 和一个显式仓库 registry。因为 Git 获取代码本来就要改，通用定位器层、自动镜像回退、缓存和鉴权挂钩看起来都是高效的未来铺垫。后来的清理犯了相反的错误：为了缩小补丁删掉了自定义 registry 支持。两种选择都在优化实现的形状，而不是要求的安装行为。

## 原因

“更可复用”和“diff 更小”都可能看起来是改进，却偏离任务。完成条件防止必需行为被删掉；明确不做什么，才能避免把额外功能变成本次必须交付的承诺。

## 例外与边界

受支持输入、治理策略或已接受契约要求的检查，即使没有逐项列出也属于完成的一部分。说明这个依据，而不是把"健壮性"或"安全性"当作无限例外。后来经授权的需求可以把原先排除的工作纳入范围，但仅凭未来可能性不行。

## 示例

在构建新加载器时，Agent 很想加上镜像、缓存和一套插件系统。它写下："完成条件：不指定覆盖参数时，安装使用官方 registry；显式指定仓库时，安装使用该自定义 registry。"又写下："不属于本任务：自动镜像回退、鉴权插件、多 registry 聚合、通用文件或 HTTP 定位器、registry 缓存。"验证必须覆盖两条必需路径；不需要实现或永久禁止那些非目标。
