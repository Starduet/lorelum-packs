# 让工作扎根在用户目标上

## 适用场景

开始任务前，先说清谁需要什么结果。如果已经埋头讨论实现，却说不清为什么要做这件事，就回到这个问题。结果已经明确、只缺“怎样才算完成”时，应先写验收条件。

## 具体指导

1. 阅读当前请求，以及已被接受、用来规定这项工作的 issue 或规格说明。
2. 用一句话说明谁需要这项改动、做完后他们能看到什么或做什么，以及会影响结果的明确约束：“创作者能找到失败的文件并重试。”
3. 用这句话判断每项提议是否有用。组件、测试、文档和抽象都是实现目标的手段，不是目标本身。现有代码里最容易改的地方，也只有能带来所需结果才值得改。
4. 两种解读会带来不同结果时，询问请求者，不要默默替对方决定。

这句话能帮你排除无助于所需结果的工作，就足够了。

## 反模式

客服人员需要凭客户报出的参考号定位延误订单。因为仓库里已有一个现成的运营看板，Agent 在上面加了个"延误"徽标并让组件测试转绿。看板能用，但客服仍然无法用客户提供的参考号搜索，打磨精美的组件错过了需要的结果。

## 原因

说清结果，后续选择才有依据。否则很容易把一个组件做完、让检查通过，却仍没解决用户的问题。

## 例外与边界

对于精确的机械性请求（如重命名一个给定的标签），请求者的措辞本身可能就是完整目标。本 Practice 只确定结果；不列举验收检查项或非目标。

## 示例

请求说改进失败上传的体验，而仓库里已有一个通用错误横幅，改文案看起来最省事。动工之前，Agent 先记录："创作者能识别失败的文件并重试，且不必重新上传已成功的文件。"这句话没有限定 UI 设计，却说明了为什么只改现成的横幅不能满足用户需要。
