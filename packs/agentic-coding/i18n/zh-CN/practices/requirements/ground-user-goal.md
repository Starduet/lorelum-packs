# 让工作扎根在用户目标上

## 适用场景

任务开始时使用；或当实现细节已经取代了做事的理由、且没有任何一句话说明"谁需要什么结果"时使用。如果结果已经清楚、只缺完成定义，应改为定义验收条件。

## 具体指导

1. 阅读当前请求和管辖它的已接受 issue 或规格说明。
2. 写一句话，点名受影响的人、他们必须能观察到的结果，以及任何改变该结果的明确约束："创作者能找到失败的文件并重试。"
3. 用这句话检验每项提议的工作。组件、测试、文档和抽象都是可能的手段而非目标；最容易上手的附近改动，只有当它能产生点名的结果时才算合格。
4. 如果对请求的两种解读会产生不同结果，向请求者要决定，而不是默默选一个。

当这句话能够否决不推进该结果的工作时停止。

## 反模式

客服人员需要凭客户报出的参考号定位延误订单。因为仓库里已有一个现成的运营看板，Agent 在上面加了个"延误"徽标并让组件测试转绿。看板能用，但客服仍然无法用客户提供的参考号搜索，打磨精美的组件错过了需要的结果。

## 原因

具体的产出给后续决策一个稳定的对照点。没有它，仓库结构和可见交付物会取代用户价值，而表层检查依然通过。

## 例外与边界

对于精确的机械性请求（如重命名一个给定的标签），请求者的措辞本身可能就是完整目标。本 Practice 只确定结果；不列举验收检查项或非目标。

## 示例

请求说改进失败上传的体验，而仓库里已有一个通用错误横幅，改文案看起来最省事。动工之前，Agent 先记录："创作者能识别失败的文件并重试，且不必重新上传已成功的文件。"这句话让 UI 设计保持开放，同时说明只改横幅——那个最容易上手的附近改动——并不能给人他们真正需要的东西。
