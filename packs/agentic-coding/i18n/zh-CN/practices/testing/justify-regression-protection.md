# 永久回归保护必须有长期理由

## 适用场景

失败或纠正已被理解、即将转化为永久测试或门槛之前使用。决策是"防复发是否值得长期维护"。它不是更早的"失败原因是什么"决策，也不是直接来自当前需求的常规正向覆盖。

## 具体指导

1. 说出提议的永久测试、否定断言、lint 规则或门槛要捕获的失败。
2. 只有存在持久理由才保留：明确承诺、必需的否定式（如"未授权请求绝不返回数据"）、真实复现过且可能随未来改动回归的 bug，或高影响的安全/隐私/兼容/数据完整性风险。"刚刚发生过"不够。
3. 选择保留、收窄、临时化还是省略该保护；临时保护要记录何时可移除。
4. 观察捕获复发的最小稳定行为，不冻结今天的 helper 设计。

把理由记录在保护措施旁边，到此为止。

## 反模式

用户拒绝 Agent 私自加在某界面上的辅助文案并要求恢复原设计。仓库有简单的文本 lint 机制，为那个短语加一条全局禁令很便宜，也让纠正显得彻底。Agent 加了禁令，但用户恢复的是一个界面，不是产品级禁令；也没有共享生成器或重复失败能把那段文案带回别处。

## 原因

回归测试和门槛把一次事故变成长期约束。持久性检查让保护留给"要紧且可能复发"的失败，避免套件被"最近哪个 Agent 错得多"的偶然性塑形。

## 例外与边界

未授权访问、秘密暴露、破坏性数据丢失、违规和已发布兼容性破坏，在一次可信事故之后就可以获得保护，因为失败代价高。迁移期间的临时防护在移除条件明确时也合适。不要为压缩测试数或 diff 大小而拒绝正当保护，也不要在未解决的失败尚未分类之前添加保护。

## 示例

用户要求支付重试最多产生一笔扣款。一个已复现的 bug 表明队列序列化器在重投前丢掉了请求标识符，导致重复扣款。因为公开支付契约要求幂等、且序列化器是未来可能重构的点，Agent 增加一个永久测试：重投保存的任务并观察只扣一次款。它不冻结当前队列 helper 的调用顺序。
