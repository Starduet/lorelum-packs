# 测试用户或调用方真正能依赖的结果

## 适用场景

已经知道测试为什么存在、准备选择检查内容时使用。先确定依赖该行为的是用户、API 调用方、持久化数据读取方、外部消费者，还是有意保持稳定的内部接口。本条选择观察位置，不判断该行为是否值得测试。

## 具体指导

用受控输入驱动行为，在最靠近真实使用方的稳定接口检查返回值、保存记录、协议消息、权限决定、文件字节等结果。细节要足以区分成功和最可能的失败，但不要重建内部执行路线。当前无法观察时，只增加最近稳定接口上的最小合法读取入口。内部重构不改变承诺行为时，断言也应继续通过。

修改校验或恢复时，确认合法路径仍可用，并在负责边界观察独立的非法或降级结果：拒绝仍是拒绝，需要标识的旧数据确实可辨，retry 用尽返回约定失败。不要要求每个内部层都调用同一个 validator，也不要单为证明防御代码必要而维护不可能出现的内部状态测试。已承诺的尝试预算或不重复执行保证属于可观察行为。

## 反模式

用户要求撤销权限后下一次请求立即失败。仓库使用授权缓存，重构在两个辅助函数间移动失效逻辑。模拟辅助函数顺序快速且稳定，Agent 便断言先失效再查找；测试可能通过但下一请求仍拿到旧的允许决定，也会在以后正确删除缓存时无谓失败。

## 原因

只有当断言失败意味着承诺可能被破坏，它才提供有用信号。观察实现细节既可能漏掉用户缺陷，也会把维护精力花在代码形状上。

## 例外与边界

精确字节、语法树、协议字段、事件顺序、时限或序列化形态本身是公开、兼容或安全要求时，就应精确断言。项目有意稳定的内部 API 也可作为边界。可观察不等于模糊。

## 示例

测试先授权并确认请求成功，再通过受支持管理入口撤销，随后从正常请求路径验证拒绝。它不查看缓存标志或辅助函数顺序，因为用户依赖的是拒绝结果。
