# 每个测试都要说明自己保护哪项契约

## 适用场景

新增或大幅修改测试、其目的还在选择之中时使用。问一句：这个测试失败时，破坏的是哪条承诺？本 Practice 在测试拥有一个明确的保护契约时结束。如何观察该契约属于断言设计；过去的 bug 是否值得永久回归测试属于回归保护判断。

## 具体指导

1. 写测试前先点名它的确切理由：用户请求中的一句话、已接受的 issue 或规格、已发布接口，或一条必要规则，例如"一个用户不能读取另一个用户的数据"。
2. 把该理由复述为行为，不点名当前的 helper 或类。
3. 仅当测试失败可能意味着该行为被破坏时才保留它。找不到有意义的理由就省略该测试，或把它标注为临时调查，而不是把新代码当作天然值得测试。
4. 把这层联系记录在测试名、就近注释或评审说明里。

当测试拥有一个明确的保护契约时停止；选择断言是下一步。

## 反模式

用户要求可安全重试的任务提交。仓库已有队列 adapter，这次改动新增了重试 helper 和状态枚举。因为每个新方法都容易覆盖、覆盖率报告又高亮其分支，Agent 每个方法写一个测试。套件全绿，但没有一个测试保护"重试同一任务不得重复提交"这条用户可见规则。

## 原因

测试比催生它的实现选择活得更久。当测试的目的来自当前代码结构时，它可能保留错误的设计却依然显得周全。测试到契约的映射让维护成本和未来失败都绑定在项目真正承诺过的行为上。

## 例外与边界

探索性探针和临时表征测试可以在不宣布其正确的情况下揭示未知行为；给它们打标，之后有意识地退役或转正。安全、兼容性和数据完整性不变量即使产品文档没提，也可以证明覆盖合理。保持映射已清晰的机械更新无需重复分析。

## 示例

用户要求上传在 worker 重启后恢复且文件不损坏。仓库现在有独立的分块调度和重试 helper，但它们是实现选择。Agent 为"重试被中断的分块不重复存储字节"和"上传在进程重启后恢复"各建一个测试，并把契约写进测试名。helper 调用模式保持不测，因为它们不是对用户的承诺。
