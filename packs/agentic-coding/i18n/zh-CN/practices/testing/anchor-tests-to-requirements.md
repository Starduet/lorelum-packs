# 每个测试都要说明自己保护哪项契约

## 适用场景

准备新增或大幅修改测试时，先问：这个测试失败，会说明哪条承诺可能被破坏？明确它保护什么之后，再决定怎么观察该行为。过去某个 bug 是否值得留下永久回归测试，则需要另行判断。

## 具体指导

1. 写测试前先点名它的确切理由：用户请求中的一句话、已接受的 issue 或规格、已发布接口，或一条必要规则，例如"一个用户不能读取另一个用户的数据"。
2. 把理由写成行为，不用当前 helper 或类的名字代替。
3. 测试失败确实可能说明这项行为被破坏，才保留测试。没有这样的理由，就不加，或明确标为临时调查；不是每段新代码都天然需要一个测试。
4. 在测试名、附近注释或评审说明里，写清测试与这项要求的关系。

说明这个测试保护哪条明确承诺后，就可以选择断言。

## 反模式

用户要求可安全重试的任务提交。仓库已有队列 adapter，这次改动新增了重试 helper 和状态枚举。因为每个新方法都容易覆盖、覆盖率报告又高亮其分支，Agent 每个方法写一个测试。套件全绿，但没有一个测试保护"重试同一任务不得重复提交"这条用户可见规则。

## 原因

实现换了，测试往往还会留下。如果测试只保护今天的代码结构，就可能保住错误设计，看起来却很周全。写清每个测试保护哪项承诺，后续维护和处理失败才有依据。

## 例外与边界

探索性探针和临时表征测试可以查明当前行为，不代表认可它是正确行为。把这种用途标清，之后明确决定删除，还是保留为长期测试。安全、兼容性和数据完整性规则即使产品文档没提，也可能需要测试。已有测试的目的清楚且未变时，机械更新不必重复分析。

## 示例

用户要求上传在 worker 重启后恢复且文件不损坏。仓库现在有独立的分块调度和重试 helper，但它们是实现选择。Agent 为"重试被中断的分块不重复存储字节"和"上传在进程重启后恢复"各建一个测试，并把契约写进测试名。helper 调用模式保持不测，因为它们不是对用户的承诺。
