# 检查失败后先判断谁错了，再改代码或测试

## 适用场景

测试、lint、类型检查、构建或验证失败，而且有不止一种合理解释时，先查原因，再改实现、期望结果、fixture、生成文件或工具配置。可能是产品有错、测试过期或写错、环境或不稳定行为影响结果、生成文件来自另一版源码，也可能是早已存在的无关失败。外部评审意见如果没有复现的检查，应按评审意见来核实。

## 具体指导

1. 用已知的 commit、构建或生成文件复现最小的相关失败。
2. 阅读失败的断言或诊断，把发生的情况与当前需求对比。
3. 检查可能改变结果的环境、输入、fixture 和生成文件，只收集足以区分主要解释的证据。
4. 记录原因，以及哪项事实排除了第二种最可能的解释。

查明问题出在哪里，再选修复方式。原因还不清楚，就保持产品代码、测试和配置不动，说明仍有哪些疑问，不要一路修改到套件变绿为止。

## 反模式

用户要求一次保留键盘导航的视觉刷新。附近的 UI 重构改了快照，新界面也好看。更新快照只需一条命令就能恢复绿色套件，Agent 立刻照做。但重构同时移除了一个必需的键盘操作，这次期望更新在行为与请求对比之前就删掉了唯一的失败信号。

## 原因

检查失败只能说明有不一致，不能直接说明哪边对。先查原因，才能避免把产品缺陷当成新的期望结果，或为了过时测试改坏正确行为，也能避免把原本就有的无关失败混进本次改动。

## 例外与边界

延迟会扩大伤害时，先遏制进行中的安全、数据丢失或生产事故，同时保留证据待查。直接确认的基础设施故障或损坏的生成文件可以修复，无需重审所有可能原因。已批准的需求变更可以使测试过期，但理由是那次批准，不是新的实现输出。

## 示例

用户要求迁移能在当前发布 schema 上工作。仓库里迁移测试单独跑通过、跟在另一个数据库套件后失败。Agent 两种顺序都跑并检查起始 schema 版本，发现前一个套件留下了共享状态。全新数据库迁移成功，所以失败来自测试隔离而非迁移本身或其期望结果。确认之后才去改共享 fixture 的清理。
