# 把安全且临时的假设明确写出来

## 适用场景

某个实现细节还没答案，但两种合理做法都安全、只影响局部、也容易替换时，可以先明确记录一种临时选择，再继续。会改变用户可见的产品含义、公共契约、安全边界或不可逆操作的选择，必须在编码前确认，不能按临时假设处理。权威来源彼此矛盾时，先确认应以哪份为准。

## 具体指导

1. 做选择时用一行记下暂时按哪种方式处理，以及为什么两种解读都合理。
2. 标明具体影响哪段代码，例如一个序列化器或导入器。依赖这项选择的工作只在这里展开，不要从临时假设推导新需求。
3. 说明什么能确定最终做法：哪份来源、哪位负责人的答复，或什么观察结果能确认或替换这个选择。
4. 新证据推翻假设时，修改这部分实现，不要为了所谓兼容性而保留猜测。

另一个工程师能找到、复核并替换这项选择，不必重新做一遍调查，就足够了。

## 反模式

用户要求新增一个导入器。其样例记录省略了空描述，而共享模型同时接受"省略"和"空字符串"。在导入器里用空字符串很快也无害，于是 Agent 顺手把共享序列化器及其测试也改成一致。一个局部临时选择现在扩散到了每个导入器，看起来像被接受的数据契约。

## 原因

代码和测试会让未记录的选择显得已定。把不确定性写下来，既保持它可见、限制其扩散，又不妨碍安全的推进。

## 例外与边界

不要用本 Practice 绕过相互冲突的需求，或绕过需要产品、安全、法务或运维审批的决策。仓库惯例已定的细节无需额外记录。

## 示例

样例报文没有说明空的可选标签应表现为"缺失"还是"空字符串"，而当前解析器两者都接受。Agent 在读取它的那个序列化器旁记录"暂时省略该字段"，说明两种形式目前都能通过，并把 schema 负责人给出的正式澄清点名为复核条件。不为了让猜测一致而改动其他序列化器或测试。
