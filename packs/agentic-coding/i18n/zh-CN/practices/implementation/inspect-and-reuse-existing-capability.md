# 新写代码前先查仓库里有没有

## 适用场景

准备创建辅助函数、adapter、parser、缓存、重试策略等很可能在附近已有的机制时使用。只查到足以判断现有行为能否满足需求。如果已有证据表明行为确实是新的，或现有方案不满足必需约束，就停止搜索并设计新代码。

## 具体指导

先看该行为应归属的模块和最接近的候选能力。只有代表性调用点或测试可能改变候选方案能否保留必需的语义、兼容性或失败约束时，才读取它。再只查最可能提供该行为的运行时或已声明依赖。决定直接复用、小幅适配或新实现；排除更接近方案时，要写出具体不匹配。证据足以支持一个选择就停，不要收集所有名字相似的辅助函数、调用方或测试。

## 反模式

导入链接要在存储前规范化。短辅助函数很容易写，示例和新测试也能过，时间紧张时直接实现很合理。但 Agent 没查看另一个导入器已用的声明依赖；后者还处理编码分隔符、主机名大小写和平台路径。仓库因此出现两套在真实输入上结果不同的规则。

## 原因

现有代码常包含从名字看不出的兼容规则、失败行为和维护归属。先检查可避免并行契约，也把新代码限制在需求真正缺少的部分。

## 例外与边界

不能只因名字合适就复用。安全边界、许可证、不支持环境、不稳定 API 或已证明的语义差异都可支持新实现。复用问题解决后，再在多个可行设计之间选择。

## 示例

排期功能需要判断新预订是否与现有预订重叠，包括共享端点。Agent 先发现排期模块已有经过测试、端点规则完全一致的函数，于是直接复用，不再定义第二套“重叠”。
