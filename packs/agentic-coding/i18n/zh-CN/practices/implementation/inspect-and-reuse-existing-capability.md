# 新写代码前先查仓库里有没有

## 适用场景

即将创建 helper、adapter、解析器、缓存、重试策略等附近很可能已存在的机制之前使用。如果当前证据已表明该行为是刻意新增、或现有选项不满足必需约束，停止搜索、直接设计新代码。

## 具体指导

1. 打开该行为所属的模块，以及其中最接近的候选能力。
2. 读取与你的预期用途最接近的调用方或测试——当候选同时服务多套不同的语义、兼容性或失败契约时，每套各读一个——以判断它是否保留你需要的约束。
3. 检查最可能提供该行为的那一个已声明依赖或运行时设施。
4. 在直接复用、小幅适配和全新实现之间做决定，并记录排除每个更近选项的具体不匹配点。

证据一旦支撑某个选择就停止；不要编目每个 vaguely 相似的 helper、调用方或测试。

## 反模式

用户要求导入链接在入库前规范化。一个短 helper 好写、符合示例、也能通过新的聚焦测试。赶工期压力下，Agent 没有检查另一个导入器已依赖的库就直接写了。那个库还处理编码分隔符、主机大小写和平台路径，于是仓库里出现了两套在真实输入上不一致的规范化规则。

## 原因

现有代码往往携带从名字看不出来的兼容规则、失败行为和维护归属。先查再建避免平行契约，也把新代码限制在当前需求真正缺少的部分。

## 例外与边界

不要仅因名字像就复用。安全边界、许可限制、不支持的环境、不稳定 API 或已证实的语义不匹配都可以证明新代码合理。复用被接受或排除之后，在多个可行设计之间做选择是另一个决策。

## 示例

排期改动需要判断新预订与既有预订是否重叠，包括共享端点的预订。Agent 先打开排期模块，发现一个已测试的重叠函数恰好带这些端点规则，于是直接复用；仓库里没有出现第二份重叠定义。
