# 新写代码前先查仓库里有没有

## 适用场景

准备写 helper、adapter、解析器、缓存、重试策略等代码时，先看看附近模块、已声明依赖或运行时是否已经能做。如果证据已经说明这是刻意新增的行为，或现有方案不满足必需约束，就停止搜索，设计新代码。

## 具体指导

1. 打开该行为所属的模块，找到其中最可能复用的代码。
2. 阅读最接近预期用途的调用方或测试。如果这段代码同时满足多种不同的行为、兼容性或失败处理要求，每种各读一个调用方或测试，确认复用后仍能满足你需要的约束。
3. 检查最可能提供该行为的那一个已声明依赖或运行时功能。
4. 决定直接复用、小幅适配还是重新实现。跳过更直接的方案时，记录它具体哪里不合适。

证据一旦支撑某个选择就停止；不要逐一盘点每个只是大致相似的 helper、调用方或测试。

## 反模式

用户要求导入链接在入库前规范化。一个短 helper 好写、符合示例、也能通过新的聚焦测试。赶工期压力下，Agent 没有检查另一个导入器已依赖的库就直接写了。那个库还处理编码分隔符、主机大小写和平台路径，于是仓库里出现了两套在真实输入上不一致的规范化规则。

## 原因

现有代码常常处理了名字里看不出的兼容规则和失败情况，也有负责维护它的地方。先查再写，能避免出现两套不一致的规则，让新增代码只补上当前需求真正缺少的部分。

## 例外与边界

不要仅因名字像就复用。安全边界、许可限制、不支持的环境、不稳定 API 或已证实的语义不匹配都可以证明新代码合理。复用被接受或排除之后，在多个可行设计之间做选择是另一个决策。

## 示例

排期改动需要判断新预订与既有预订是否重叠，包括共享端点的预订。Agent 先打开排期模块，发现一个已测试的重叠函数恰好带这些端点规则，于是直接复用；仓库里没有出现第二份重叠定义。
