# 在真正负责该事实的边界做校验

## 适用场景

沿数据路径新增或审视重复检查时使用。问题是"这个位置能否遇到不同的非法状态"，而不是"校验一般是否有用"。已知失败之后怎么办是另一个恢复决策。

## 具体指导

1. 只追踪相关的输入及其交接。说出每个既有检查建立的事实、它最早在哪里变得可信、以及负责维持它的组件。
2. 把每个检查指派到其归属边界：外部形状在入口校验；业务规则在其状态归属处应用；在拥有该转换的地方一次性规范化为约定表示；已确立的结果经普通内部调用传递。内部类型应在可行处表达该结果；一个 cast 本身什么也没确立。
3. 新增检查前，先找出"在这个位置什么可能使早前结果失效"：另一个入口、不可信反序列化、一次转换、并发修改、过期的授权，或独立要求的保护。只有存在这种条件才保留检查——新的函数、层或包名本身不是新边界。
4. 把多余的拒绝、维护、延迟和恢复代价与该检查阻止的不同失败对比。

以"每个事实有清晰归属 + 实际路径只需要这些检查"结束；在现有设计或评审里一段简短说明就够。

## 反模式

HTTP
adapter 把数量解析成正整数。服务、领域 helper 和仓库各自接收这个类型化值，却又分别解析、钳制和拒绝它，因为每个模块都"要健壮"。它们的上限后来分叉：adapter 接受批量订单，某个隐藏 helper 却悄悄钳制。每层都有测试，但有效请求在接受之后被改变，调用方无法分辨哪条规则定义了订单。

## 原因

检查只有在"建立一件在那里可能为假的事"时才有价值。重复已确立的事实只会制造更多规则归属、失败路径和维护，却不改善保证。不同边界即便检查同一字段，仍可能需要不同保护。

## 例外与边界

API 和 CLI 可以在共享类型化领域调用前各自校验原始输入。预检无法防止并发插入时，数据库唯一性约束依然必要。反序列化排队消息的 worker 有新的输入边界；传给私有 helper 的未变对象没有。HTML 输出编码解决的是与输入解析不同的问题。

评估鉴权规模时使用已确认的部署与调用方事实。位于强制网关之后的内部服务不必为每个 helper 复刻身份平台；可绕过的网关或跨租户操作可能需要自己的鉴权决定。保留有独立理由的纵深防御和显式政策要求。移除既有检查前先弄清其调用方和契约；本 Practice 本身不授权改变已接受的行为。

## 示例

库存服务通过 HTTP 端点和 CSV 导入接收订单。每个 adapter 解析原始数量并创建同一个类型化命令。领域服务检查当前可用库存，数据库原子地防止竞争预留导致超卖。Agent 保留这些不同的检查，并删掉仓库里提议的第三个字符串解析器：没有字符串或未检查的调用方能到达它。库存变更仍在修改边界被检查，而已解析的数量直接传递、不再经过另一套规范化政策。
