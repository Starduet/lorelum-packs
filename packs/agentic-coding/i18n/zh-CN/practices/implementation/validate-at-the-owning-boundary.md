# 在真正负责该事实的边界校验

## 适用场景

准备增加防护，或检查一条数据路径上的重复校验时使用。判断的是这个位置是否可能遇到独立的非法状态，而不是泛泛讨论校验有没有用。已知失败后如何恢复，是另一个决定。

## 具体指导

只追踪相关输入和交接。说明每项检查建立什么事实、它在哪里首次可信，以及哪个组件负责保持它成立。外部数据格式在入口校验，业务规则放在负责相关状态的组件，普通内部调用直接传递已经建立的结果。规范化在负责转换的位置做一次，并尽量用类型表达结果；单靠类型断言不能证明数据有效。

增加下一层检查前，指出什么会使前面的结果失效：另一个入口、不可信反序列化、数据变换、并发修改、授权过期，或独立要求的保护。保留覆盖这些条件的检查。新函数、新层或新包的名字本身不构成新边界。把额外拒绝、维护、延迟和恢复成本与它防止的独立失败比较。明确负责人、仅留下真实路径所需的检查后停止；在现有设计或审查里简短说明即可。

## 反模式

HTTP adapter 已把数量解析为正整数。service、domain
helper 和 repository 接收同一个有类型的值，却为了各自健壮而再次解析、截断和拒绝。后来上限发生偏移：入口接受的大批量订单被内部 helper 静默缩小。各层都有测试，但合法请求在接受后被修改，调用方无法判断哪套规则才定义订单。

## 原因

检查的价值在于建立一个在当前位置确实可能不成立的事实。重复已经成立的事实会增加规则负责人、失败路径和维护，却不增强保证。真正不同的边界即使检查同一个字段，也可能需要各自的保护。

## 例外与边界

API 和 CLI 可以分别校验原始输入，再调用共同的有类型 domain 接口。预检查不能防止并发写入时，数据库唯一约束仍有必要。worker 反序列化队列消息形成新输入边界，原样传入私有 helper 的对象则没有。HTML 输出编码与输入解析解决的也不是同一个问题。

按已确认的部署与调用方事实决定鉴权深度。位于强制网关后的内网服务不必为每个 helper 重建身份平台；网关可绕过或涉及跨租户操作时，可能仍需独立授权。保留有独立理由的纵深防御和明确政策要求。删现有检查前先确认调用方和契约，本条不单独授权改变已接受行为。

## 示例

库存服务从 HTTP 和 CSV 导入接收订单。两个 adapter 分别解析原始数量，建立相同的有类型 command；domain
service 检查当前库存，数据库原子防止并发预留导致超卖。Agent 保留这些不同检查，取消 repository 中拟增加的第三次字符串解析，因为没有字符串或未校验调用方能到达那里。库存变化仍在修改边界检查，已解析数量直接传递，不增加新的规范化策略。
