# 在真正负责该事实的边界做校验

## 适用场景

同一份输入经过 adapter、服务和存储层，你需要决定在哪检查，或后面是否还要再查一次时，沿实际调用路径判断，不必遍历每个包。新检查增加的保护是否值得其成本，由
`justify-added-checks` 处理。已知失败后该重试还是回退，则是恢复问题。

## 具体指导

1. 只跟踪相关输入或状态及其传递过程。对每个检查说明：这里可能怎样出错，或哪项强制契约要求检查；检查能证明什么；最早从哪里可以信任这个结果；哪个组件负责让它继续有效。
2. 外部输入的结构在入口检查，业务规则由负责相关状态的组件执行。由负责转换的地方一次性转成约定格式，再通过普通内部调用传递结果。可行时用内部类型表达已经检查过的结果；只做类型强制转换不算验证。
3. 再查一次之前，先说明什么可能让之前的结果在这里失效：另一个入口、不可信的反序列化、数据转换、并发修改、授权过期，或独立要求的保护。存在这类条件才保留检查。多一个函数、层或包名，本身不代表多了一个边界。
4. 调用没有改变结果，就直接传递；真正不同的边界仍要保留各自的检查。删除内部重复工作，不要为了继续做重复检查而增加缓存、可信标记或锁。

明确每项保证由谁负责，只留下实际路径需要的检查，就可以停止；在现有设计或评审里简短说明即可。

对于受控的内部数据生产方，可以依赖其契约和真实生产路径保证的输出条件。跨进程或调用本机 HTTP，本身不会让输出变成不可信数据。必要的解码、认证、协议匹配、请求与响应关联仍要检查，但不必因此重新遍历整个业务 schema。数据表示转换只需检查它可能引入的失败，不是检查任意对象可能出现的一切问题。

不要默认让生产代码防范另一层内部实现违反自己的类型和契约。优先使用类型、生产方契约测试和必要的开发期断言。mock 捏造了生产方不可能输出的结果，不能成为下游加防御的理由。外部输入、真实损坏和受支持恢复路径的测试仍须保留。

JSON 解码并验证后，如果没有引入新值，再检查循环引用、Symbol 或任意对象原型并不会多提供保证。真正负责转换或生命周期的适配层要保留；不同边界不必共用一个万能校验器。先前的检查不覆盖后来的文件变化，也不覆盖能绕过已检查路径的新调用方。

保留外部输入验证、模型/native 接入质量检查、发布完整性、事务与快照一致性、认证、进程归属和损坏派生缓存的重新生成能力。现有契约要求的检查，必须先按正常流程修改契约，才能删除。

## 反模式

HTTP
adapter 把数量解析成正整数。服务、领域 helper 和仓库收到这个有明确类型的值，却又各自解析、钳制和拒绝它，理由是每个模块都“要健壮”。它们的上限后来不一致：adapter 接受批量订单，隐藏的 helper 却悄悄减小数量。每层都有测试，但有效请求在接受后被改变，调用方不知道到底应以哪条规则为准。

## 原因

检查能确认一个在当前位置确实可能不成立的条件，才有价值。重复确认已经成立的事实，只会增加规则的维护方、失败路径和维护工作，并不增强保证。不同边界即便检查同一字段，仍可能需要不同保护。

## 例外与边界

API 和 CLI 可以在共享类型化领域调用前各自校验原始输入。预检无法防止并发插入时，数据库唯一性约束依然必要。反序列化排队消息的 worker 有新的输入边界；传给私有 helper 的未变对象没有。HTML 输出编码解决的是与输入解析不同的问题。

评估鉴权规模时使用已确认的部署与调用方事实。位于强制网关之后的内部服务不必为每个 helper 复刻身份平台；可绕过的网关或跨租户操作可能需要自己的鉴权决定。保留有独立理由的纵深防御和显式政策要求。移除既有检查前先弄清其调用方和契约；本 Practice 本身不授权改变已接受的行为。

## 示例

库存服务通过 HTTP 端点和 CSV 导入接收订单。每个 adapter 解析原始数量并创建同一个类型化命令。领域服务检查当前可用库存，数据库原子地防止竞争预留导致超卖。Agent 保留这些不同的检查，并删掉仓库里提议的第三个字符串解析器：没有字符串或未检查的调用方能到达它。库存变更仍在修改边界被检查，而已解析的数量直接传递、不再经过另一套规范化政策。
