# 新增检查前先说明理由

## 适用场景

规划或实现普通任务时，你可能想“保险起见”加一个预检、校验、权限确认、完整性扫描或阻断条件。先判断它有没有用，再动手实现，不要等到最终评审。请求里即使没提门槛、重复检查或成本，也要做这个判断。第一次加的检查即使没有重复工作、没有让正常流程走不通，也可能带来问题。

## 具体指导

1. 说清不加检查会怎样出错：什么输入、调用方、状态变化或故障可能到达这个操作，谁会受损。另行说明有没有强制契约或政策要求。“安全风险”这类标签不能说明失败是怎么发生的。
2. 找到负责防止这种失败的组件，确认已有保护。入口校验、数据生产方的保证、授权、事务、安装或发布已经检查了什么？使用之前，什么变化可能让这些保证失效？本机地址、类型转换或早前做过检查，都不能单独证明它们仍然有效。
3. 说明新检查能捕获哪种现有保护会漏掉的失败。这里是否新增了信任边界、数据转换或并发状态变化，还是只把同一规则再查一遍？安全或数据丢失风险还不明确时先调查，不能把未知当作不存在。
4. 比较额外保护与检查自身的影响：误拒绝、延迟与 I/O、维护、服务不可用，以及启动、升级、停止或修复受阻。实际成本可能改变选择时做有界观察；不要求例行 benchmark 或风险报告。
5. 新增或保留必要保护；否则收窄范围、选择足够的非阻断响应，或在不削弱所需保障的前提下调整检查的位置或时机，也可以不加检查。在现有设计或评审中简要记录理由。目标不是检查更少。

实现前，把这项检查为什么该加或不该加说清即可。如果已经确定必须检查，只是不知道放在哪里，就决定由哪个组件负责。如果几项必要检查需要组合成可用流程，就走查用户完成任务的整条路径，不必重新讨论每项检查是否必要。

## 反模式

普通后端任务让 Agent 为每次启动增加整个模型目录的哈希扫描，为每个受控 HTTP 响应增加完整业务 schema 遍历，为修复增加健康服务探针。每项都被称作更安全，却没人指出它们比选定模型的 loader、响应生产方的已确立契约，或修复自己的身份与权限检查多保护了什么。无关文件拖慢启动，有效结果多了一套拒绝规则，服务故障时修复反而不能运行。只在实现完毕后逐项评审，错过了更早的取舍时机。

## 原因

看似合理的防护可能增加工作和拒绝路径，却没有补上真实缺口。把必要性独立为一个决策，能在 Agent 采纳提案之前检查它；之后把检查放对位置、证明主路径可通，都不能回答最初是否应该增加它。

## 例外与边界

必需的安全、数据一致性和契约是取舍约束；成本高不授权删除。保留外部输入检查、资源专属授权、并发状态的原子保护、必需的 native/model 质量与发布完整性，以及恢复身份保障。有独立理由的纵深防御仍然有效。已接受的检查契约须由其负责人按正常流程修改，不能悄悄把失败降为警告。

本条不是生产旁路、新的用户审批要求，也不是全面禁止启动扫描。可变的导入模型可能需要不可变安装不需要的验证。修复操作可以不依赖业务就绪，但仍须建立自己的授权、身份和修改安全条件。类型和契约测试不能替代真实信任边界。

## 示例

任务把桌面客户端接到随附的本机 worker。worker 构造已验证记录，会话已认证，响应在序列化后不会再变。Agent 在增加第二次完整业务 schema 遍历之前，找不到它能捕获的新失败，因此不加；解码、协议匹配、身份和请求关联仍保留。公开导入入口仍须验证任意 JSON，不能继承随附 worker 的保障。

只读桌面启动准备第一次增加磁盘剩余空间门槛，理由是以后也许会增加导出。它没有重复检查，也没有引入依赖循环。Agent 在编码前否决：启动没有大量写入，已接受的契约也不要求这个门槛，受支持的只读会话会多一条拒绝理由，却没有新增保护。必需的启动输入、native/model 和发布完整性检查仍保留；可变模型仍须防护验证与使用之间的变化。
