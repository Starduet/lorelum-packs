# 说清失败后怎样恢复、由谁负责

## 适用场景

准备加上重试、改用其他数据或默认值兜底，或捕获错误后继续运行时，先分清哪些错误确实能恢复，以及恢复后该返回什么。保留已有处理方式时也要这样判断。输入校验是另一个问题：即使输入合法，依赖的服务不可用时，操作仍会失败。

## 具体指导

1. 先说清正常情况下，操作成功或失败时，调用方分别会收到什么。
2. 找出哪种已知失败能通过重试或兜底解决，并由一个组件负责这项恢复。
3. 说明恢复后哪些结果或已有状态仍可使用；如果它与直接成功、取得最新数据有重要差别，也要让调用方知道。
4. 准备重试时，先说明为什么再试可能成功、会不会把同一件事做两遍，再定总尝试次数或总耗时上限。检查客户端、任务和调用方是否已经在重试，不要让各层的次数相乘。
5. 准备用其他来源兜底时，确认它能提供等价结果，或较差的结果及其限制已经被明确接受。否则就返回原有错误，不能把数据格式错误、没有访问权限或写入失败伪装成空列表或默认值。

在本来负责对外返回错误的组件里转换错误，保留调用方据以处理问题的原因。恢复操作只应要求安全执行它所必需的条件。可选输入缺失时用已约定的默认值，不需要因此搭建一套恢复框架。

哪个组件负责恢复哪些失败、最多重试多久或多少次、兜底有什么限制、调用方最后看到什么，都说清楚后就可以结束判断。如果不需要恢复，就在面向用户的接口直接报错，给出可用的下一步。

## 反模式

仪表盘要显示当前失败任务数。HTTP 客户端最多尝试三次，服务端又最多调用它三次；外面再包一层，遇到任何异常都先用旧缓存，缓存也没有就返回空列表。代码很少报错，看起来很可靠。服务故障时，它却先发九个请求，再显示“零个失败任务”。运维分不清系统健康还是数据根本没取到，连无关的解码错误也一起被掩盖。

## 原因

兜底会改变产品在出错时的表现，本身也可能出错。每种错误都返回默认值，会让坏掉的系统看起来正常；多层重试则把延迟和负载成倍放大。交给一个组件负责，才能说清结果和限制。

## 例外与边界

已经接受的离线模式、允许读取较旧数据的策略、兼容方式，以及可选配置缺失时的默认值，不该一概删除。保留已约定的限制，并确认结果符合要求。不同操作各自重试也可以，但仍须遵守总预算。

写入后超时时，数据可能已经提交。应通过幂等保证避免重复执行，或先核对操作结果，不能盲目重放。强制审计或完整性检查失败，也不能靠兜底变成成功。

## 示例

状态页允许在网络传输故障时显示生成于五分钟以内的快照。数据客户端负责有限次数的重试；页面只在这种已知故障下使用带时间戳的缓存，并注明数据不是最新的。缓存超过五分钟、没有访问权限或报文格式错误时，仍明确报错。

再看本地停止进程的命令：即使进程的业务 API 与客户端不兼容，命令也应能停止它。它仍要检查是不是目标进程，但不应要求先成功查询业务数据。两种恢复都不需要一层层通用兜底。
