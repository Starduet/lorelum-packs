# 让恢复有明确负责人和可理解的结果

## 适用场景

准备新增或保留 fallback、retry、吞错误封装时使用。决定哪种已知失败能够恢复，以及调用方最终拿到什么。在什么位置校验输入是另一个问题；有效输入也可能遇到依赖不可用。

## 具体指导

先看正常成功和失败契约。指出可恢复的具体条件、负责恢复的组件，以及能够交付的可用结果或保住的状态。没有已接受恢复行为时，优先传递既有错误。不要把损坏数据、权限拒绝或写入失败换成空列表或默认值，制造成功。

retry 必须说明下一次为何可能成功、重复执行是否会重复副作用，并确定整体次数或时间预算。新增前检查 client、job 和调用方已有的 retry，避免预算相乘。fallback 必须说明替代来源等价，或降级已被明确接受，并说明限制及调用方如何知道重要差异。契约已定义的可选输入缺省值不需要恢复框架。

由负责接口的层翻译错误，并保留可行动的原因。恢复操作只依赖安全完成该操作所需的前提。负责人、适用失败、有界恢复和最终可观察结果明确后停止。不需要恢复时，保留直接失败，在用户边界提供可执行的下一步。

## 反模式

看板必须显示当前失败任务数。HTTP
client 最多尝试三次，service 最多执行三轮 client 调用，wrapper 遇到任何异常又从旧缓存退到空列表。代码看起来很有韧性，也很少报错；依赖故障时却先发九次请求，再显示零失败。运营无法区分系统健康还是缺少数据，解码 bug 也被同一路径掩盖。

## 原因

恢复是额外产品行为，也会产生失败方式。没有明确条件的 fallback 会把可发现错误变成假成功，多层 retry 则放大延迟和负载。统一负责人才能让结果可理解、预算可执行。

## 例外与边界

已接受的离线模式、旧数据读取策略、兼容路径或可选配置默认值是有用行为，不自动属于冗余；保留其限制并验证结果。不同操作的独立 retry 若符合总体预算，可以保留。可能已经写入后的超时需要幂等或结果核对，不能盲目重放。强制审计或完整性失败不能靠 fallback 变成成功。

## 示例

状态页允许网络故障时展示五分钟内的快照。data
client 统一负责一次有界 retry；页面仅对这一已知故障使用带时间戳缓存，并标明旧数据。过期缓存、权限错误和非法 payload 仍明确失败。另一个本地进程停止命令需要在业务 API 不兼容时仍可用：保留停止正确进程所需的身份检查，但不要求先成功执行业务 query 才允许恢复。两条路径都不需要通用的多层 fallback。
