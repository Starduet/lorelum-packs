# 让恢复有明确负责人和可理解的结果

## 适用场景

新增或保留兜底、重试或吞错的包装之前使用。决定哪个已知失败可以恢复、恢复之后调用方收到什么。在哪里校验输入数据是另一个问题；合法输入仍可能遇到不可用的依赖。

## 具体指导

1. 先写下正常的成功与失败契约：操作成功和失败时调用方分别收到什么。
2. 点名具体的可恢复条件——哪个已知失败真能恢复——并让恢复只有一个负责组件。
3. 说明恢复产生的可用结果或保留状态，以及调用方如何得知它与全新成功的实质差别。
4. 对重试：说明为什么再试一次可能成功、重放是否可能重复副作用，并定一个总尝试次数或时间预算。新增之前先检查既有的客户端、任务和调用方重试，不要叠加预算。
5. 对兜底：确立来源等价性或明确接受的降级及其上限。没有已接受的恢复时优先传播既有错误；绝不把畸形数据、拒绝访问或写入失败替换成空集合或默认值。

错误翻译留在拥有它的接口处并保留可行动的原因；恢复操作只依赖安全完成该操作所需的前提。契约已定义的"可选输入缺失用默认值"不需要恢复框架。

当"一个负责人、合格的失败集合、有界的恢复、最终可观察的结果"都清楚时停止。如果不需要恢复，就在面向用户的边界保留直接失败和可用的下一步。

## 反模式

仪表盘要显示当前失败任务数。它的 HTTP 客户端允许三次尝试，服务端最多发起三次完整客户端调用，一个包装在任何异常时从过期缓存一路兜底到空列表。代码看起来有韧性、也很少报错。故障期间它发出九个请求然后报告零失败；运维无法区分健康系统和数据缺失，一个无关的解码 bug 也被同一路径掩盖。

## 原因

恢复是额外的产品行为，有自己的失败模式。无条件的兜底能把可检测的失败变成假成功，嵌套重试则放大延迟和负载。一个明确的负责人让结果可理解、预算可执行。

## 例外与边界

已接受的离线模式、过期读策略、兼容路径或可选输入缺失的默认值是有用行为，不是天然多余。保持其声明上限并验证其结果。覆盖不同操作且符合总预算的独立重试可以保留。可能已提交写入之后的超时需要幂等性或结果对账，而不是盲目重放。强制审计或完整性失败不能通过兜底变成成功。

## 示例

状态页在传输故障期间可以显示最多五分钟旧的快照。数据客户端拥有一次有界重试；页面仅对该已知故障使用带时间戳的缓存，并为过期结果打标。过期缓存、权限错误和非法报文仍是显式失败。另一个例子：本地停止进程的命令必须在该进程业务 API 不兼容时也能工作——它保留停止目标进程所需的身份检查，但不要求业务查询成功才能恢复。两条路径都不需要一串通用兜底。
