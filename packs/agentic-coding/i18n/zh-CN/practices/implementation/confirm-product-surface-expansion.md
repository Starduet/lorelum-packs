# 暴露新能力前确认用户能依赖什么

## 适用场景

让新的 UI 选项、API 取值、配置键、存储值、导出、来源类型或扩展点在实现之外可依赖之前使用。功能的"大类"已获授权；确切的公共取值或行为还没有。完全计划外、会改变范围/风险/验证需要的功能需要的是重做计划。不暴露任何新内容的内部抽象只是设计选择。

## 具体指导

1. 阅读授权该功能的用户请求、已接受 issue 或当前规格，列出它点名的确切取值和行为。
2. 把这份清单与本变更之后用户、集成方、存储数据或下游代码可能依赖的内容对比——事件名、header、模式、token、配置键。
3. 只暴露来源支持的部分。含糊的变体保持私有，或在发布前请求决策。
4. 记录更宽义务的来源：既有的已发布契约、获批迁移或明确的平台要求，可以授权比当前功能更多的变体。

以一份明确的"现在准入的公共取值或行为"清单结束。批准一个事件、一个设置或一种来源类型，从来不等于授权任意扩展性。

## 反模式

用户要求集成方接收一个"订单已发货"webhook。仓库的事件分发器本来就接收任意事件名和 header，于是暴露这个通用形状看起来比新增一个窄事件更干净，请求的场景也能通过。但发布每个名字、自定义 header 和插件挂钩，等于让产品对用户从未要求的行为做出承诺。

## 原因

一旦用户、集成方、存储数据或下游代码依赖某个取值或行为，移除或修改它就变得昂贵。确认确切边界，防止一个通用的内部实现悄悄定义产品政策。

## 例外与边界

本 Practice 不禁止面向未来的内部设计；它只限制"现在"什么对外可依赖。

## 示例

已接受的设计要求一个显示密度设置，包含紧凑和舒适两种模式。组件可以接收任意间距 token，但没有任何用户请求或规格让这些 token 公开。Agent 只暴露两个点名的模式，自定义 token 保持内部，直到产品决策授权。
