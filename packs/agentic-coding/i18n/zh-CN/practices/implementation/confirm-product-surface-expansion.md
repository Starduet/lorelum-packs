# 暴露新能力前确认用户能依赖什么

## 适用场景

功能已经获准，但请求没有说清应提供哪些选项或取值时，先确认再发布。UI 控件、API 取值、配置键、存储值、导出、来源类型和扩展点一旦对外提供，就可能被别人依赖。如果整个功能都不在计划内，并且会改变范围、风险或检查要求，应先重做计划。不对外增加任何能力的内部抽象，只需按设计问题处理。

## 具体指导

1. 阅读授权该功能的用户请求、已接受 issue 或当前规格，列出其中明确要求的取值和行为。
2. 对照本次改动后用户、集成方、存储数据或下游代码可能依赖的内容，例如事件名、header、模式、token 和配置键。
3. 只公开有依据的部分。还不明确的变体先留在内部，或在发布前请有权决定的人确认。
4. 如果需要公开更多变体，记录依据。既有的已发布契约、获批迁移或明确的平台要求，可能要求提供当前功能暂时用不到的变体。

明确列出本次允许对外提供的取值或行为后停止。批准一个事件、一个设置或一种来源类型，不等于允许对外开放任意扩展。

已有脚手架、闲置 package 或可用传输机制，只能说明技术上能做，不能说明可以发布新集成。遵循已接受的产品接入方式。例如，产品规定优先通过已发布的 CLI 命令和宿主原生 skill 集成，就不能因为有脚手架而增加本地服务或协议包装层。批准远程接口，也不等于批准本地接口。删除脚手架时，删除仍在介绍它的过时指导，但保留仍然有效的产品约束。这个例子来自来源仓库的策略，不要求所有产品都优先通过 CLI 集成。

## 反模式

用户要求集成方接收一个"订单已发货"webhook。仓库的事件分发器本来就接收任意事件名和 header，于是暴露这个通用形状看起来比新增一个窄事件更干净，请求的场景也能通过。但发布每个名字、自定义 header 和插件挂钩，等于让产品对用户从未要求的行为做出承诺。

## 原因

一旦用户、集成方、存储数据或下游代码依赖某个取值或行为，移除或修改它就变得昂贵。确认确切边界，防止一个通用的内部实现悄悄定义产品政策。

## 例外与边界

内部设计可以为未来留余地；这里限制的是现在公开哪些内容，让外部可以依赖。

## 示例

已接受的设计要求一个显示密度设置，包含紧凑和舒适两种模式。组件可以接收任意间距 token，但没有任何用户请求或规格让这些 token 公开。Agent 只暴露两个点名的模式，自定义 token 保持内部，直到产品决策授权。
