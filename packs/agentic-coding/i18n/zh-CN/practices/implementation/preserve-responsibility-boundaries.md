# 把共享规则放进真正负责的组件

## 适用场景

同一条规则必须在多个调用方、接口或层之间保持一致、而它该归属哪里不清楚时使用。规则已在负责组件内部的局部细节是近失场景。本 Practice 选择负责组件；不重新设计架构，也不选择该组件内部最不复杂的实现。

## 具体指导

1. 用一句话说出必须保持成立的规则——不可超卖的不变量、发票总额的舍入规则。
2. 列出依赖它的每个入口：界面、API 路径、批量导入器、其他服务。
3. 把最终决定放进已对相关数据或策略负责的组件。其他层可以翻译输入、输出或呈现，但不得重新定义规则。
4. 如果没有哪个现有组件能诚实地拥有该规则，停下来做架构决策，而不是选最好改的文件。

以"一个负责组件 + 给调用方的清晰指示"结束。

## 反模式

用户要求新的结账界面显示发票最终总额。界面手头就有所有行项目，就地计算并舍入总额既免去服务改动又能让 UI 测试快速通过。但退款和 API 创建的订单仍使用定价组件的另一套舍入规则，同一张发票可能有两个总额。

## 原因

由负责组件执行的规则对每个入口只有一个含义。把它放进顺手的调用方，就把规则绑死在一条流程上，其他调用方可以绕过它或另行复刻。

## 例外与边界

不同的输入或信任边界可能需要对同一字段的检查，但每处必须建立"在那里可能为假"的事实，并强化而非重定义权威规则。把未改变的已校验值再传一层不产生这种需要。防并发修改的数据库约束可以在输入校验之后依然必要。性能驱动的复制需要证据和保持结果一致的策略。如果需求有意移动归属或拆分领域，把它当作有迁移后果的架构变更。

## 示例

仓库通过 API 和批量导入器两条路创建库存预留。可用库存由库存组件维护，于是 Agent 把不可超卖检查放在那里，让每个调用方翻译自己的输入。两个入口得到同一个预留决定，而无需复制库存算术。
