# 把共享规则放进真正负责的组件

## 适用场景

多个调用方、接口或层都必须遵守同一规则，却还不知道在哪里执行这条规则时，先决定由谁负责。如果负责的组件已经明确，只是改它内部的细节，就不必重新讨论归属。这里解决“谁负责”，不重新设计架构，也不替组件选择最简单的内部实现。

## 具体指导

1. 用一句话说清规则，例如“库存预留不能超过可用库存”，或“发票总额按这套规则舍入”。
2. 列出依赖它的每个入口：界面、API 路径、批量导入器、其他服务。
3. 由已经负责相关数据或策略的组件作最终判断。其他层可以转换输入、输出或显示形式，但不能另定一套规则。
4. 如果没有哪个现有组件能合理承担该规则，停下来做架构决策，而不是选最好改的文件。

确定一个负责组件，并写清调用方应如何使用它后停止。

## 反模式

用户要求新的结账界面显示发票最终总额。界面手头就有所有行项目，就地计算并舍入总额既免去服务改动又能让 UI 测试快速通过。但退款和 API 创建的订单仍使用定价组件的另一套舍入规则，同一张发票可能有两个总额。

## 原因

由负责组件执行的规则对每个入口只有一个含义。把它放进顺手的调用方，就把规则绑死在一条流程上，其他调用方可以绕过它或另行复刻。

## 例外与边界

不同输入或信任边界可能都要检查同一字段，但每次检查都要针对该处确实可能出错的情况，并遵守原有规则，不能另起一套。已验证的值原样传过一个内部层，不构成再检查的理由。输入校验之后，防止并发修改的数据库约束仍可能必要。为了性能而复制逻辑，需要证据，也需要保持结果一致的方法。如果需求有意转移职责或拆分领域，应按架构变更处理，并考虑迁移后果。

## 示例

仓库通过 API 和批量导入器两条路创建库存预留。可用库存由库存组件维护，于是 Agent 把不可超卖检查放在那里，让每个调用方翻译自己的输入。两个入口得到同一个预留决定，而无需复制库存算术。
