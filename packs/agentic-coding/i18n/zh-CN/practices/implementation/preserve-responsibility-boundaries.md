# 让负责数据或规则的组件统一作决定

## 适用场景

同一规则必须对多个调用方、界面或层都成立，却不清楚应放在哪里时使用。已经位于负责组件内部的局部细节不适用。本条只选择负责组件，不重做整体架构，也不选择组件内部的最简实现。

## 具体指导

写清必须始终成立的规则，并列出依赖它的入口。找到已经负责相关数据或策略的组件，把最终决定放在那里；其他层可以转换输入、输出或展示，不能另写一套规则。最后明确唯一负责组件和调用方应怎样使用它。若没有现有组件能合理负责，先请求架构决定，不要选最方便编辑的文件。

## 反模式

新结账页需要显示最终发票总额。页面已经拿到全部明细，在 UI 里计算和取整能避免改服务，测试也很快通过。但退款和 API 创建订单仍使用计价组件的另一套取整，同一张发票便可能出现两个总额。

## 原因

由负责组件统一执行，规则对所有入口只有一种含义。放在方便的调用方，会让其他入口绕过或重新实现并产生差异。

## 例外与边界

不同输入或信任边界可能需要检查同一字段，但各自必须建立一个在当地确实可能不成立的事实，且只能强化同一规则，不能重新定义。原样传递已校验值到另一个内部层不构成这种需要。防止并发修改的数据库约束在输入校验后仍可能必要。出于性能的重复需要证据和保持一致的方案。有意转移职责或拆分领域属于带迁移影响的架构变化。

## 示例

API 和批量导入器都能创建库存预留，而可用库存由库存组件维护。Agent 把“不得超卖”检查放进该组件，让两个入口各自转换输入；两者获得同一个预留决定，不复制库存计算。
