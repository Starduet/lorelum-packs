# 旧的验证结果只用于它仍覆盖的文件和环境

## 适用场景

想在代码、配置、依赖、构建产物、运行环境或相关外部条件可能已变化之后引用早前的通过结果时使用。判断旧结果是否仍描述现在要交付的东西。把证据映射到验收问的是"结果覆盖哪条需求"；解决缺口问的是"没有足够结果时怎么办"。

## 具体指导

1. 为每个打算引用的早前结果写下它到底测试了什么：commit 或 diff、构建或生成的文件、相关的配置和依赖版本、要紧时的机器或服务、变化中外部事实的观察时间，以及行使的行为。
2. 把这些细节与当前交付物逐项变更对比。
3. 把每个结果标记为"现在可用""已过期"或"不受后续变更影响"，并说明理由。
4. 只重跑结论可能改变的检查；交付的文件变了就重新构建并复查。

当每个打算引用的早前结果都有了这项决定时停止。

## 反模式

用户要求一个别的应用能打开的归档。仓库通过了兼容性检查，随后 Agent 做了一次序列化上的"小清理"。改动看起来机械、外部检查又慢，于是引用早前的通过。交付的字节现在来自兼容性结果从未行使过的代码。

## 原因

一次通过描述的是特定条件下的特定文件，不是任务上的永久徽章。记录这些细节防止旧结果为已变更的工作作证，也避免在后续改动不可能影响观察时浪费重跑。

## 例外与边界

未变化的事实可以在无关编辑后继续使用。只改文档通常不使解析器单元测试失效；改了解析器代码则使早前的二进制测试失效。安全、破坏性操作、发布和依赖在线环境的结果可能需要更频繁的新检查。即使改动看起来无关，也要遵守项目强制的重跑规则。

## 示例

用户要求一个能安装 Pack 的编译版 CLI。commit
A 构建的二进制通过了真实安装测试。后来的仅注释编辑使该结果保持可用。当参数解析在 commit
B 变更时，Agent 重新构建二进制并重复安装检查；B 上的源码级单元测试不能证明 A 的旧二进制代表当前代码。
