# 旧的验证结果只用于它仍覆盖的文件和环境

## 适用场景

早前检查通过了，但代码、配置、依赖、构建文件、运行环境或相关外部条件可能已经变化。引用那次通过之前，先确认它是否仍能说明现在要交付的东西。它证明了哪条验收要求、没有足够结果时该怎么办，是另外两个问题。

## 具体指导

1. 为每个打算引用的早前结果写清它测试的对象和条件：commit 或 diff、构建或生成的文件、相关配置和依赖版本；必要时还包括机器或服务、会变化的外部事实的观察时间，以及实际检查过的行为。
2. 对照当时检查的内容和现在要交付的内容，逐项考虑后来的改动。
3. 说明每个结果是现在仍可用、已经过时，还是不受后续改动影响，并给出理由。
4. 只重跑结论可能改变的检查；交付的文件变了，就重新构建并检查那份文件。

每个打算引用的早前结果都作出这个判断，就可以停止。

## 反模式

用户要求一个别的应用能打开的归档。仓库通过了兼容性检查，随后 Agent 做了一次序列化上的"小清理"。改动看起来机械、外部检查又慢，于是引用早前的通过结果。但交付的字节现在来自修改后的代码，那次兼容性检查并没有运行过这版代码。

## 原因

一次通过只说明特定文件在特定条件下的表现，不会让任务从此永久算作已验证。记清这些条件，才能避免用旧结果证明新代码，也不必为确实无关的改动重复检查。

## 例外与边界

未变化的事实可以在无关编辑后继续使用。只改文档通常不使解析器单元测试失效；改了解析器代码则使早前的二进制测试失效。安全、破坏性操作、发布和依赖在线环境的结果可能需要更频繁的新检查。即使改动看起来无关，也要遵守项目强制的重跑规则。

## 示例

用户要求一个能安装 Pack 的编译版 CLI。commit
A 构建的二进制通过了真实安装测试。后来只改注释，结果仍然可用。当 commit
B 改了参数解析，Agent 重新构建二进制，再做安装检查；B 上的源码级单元测试不能证明 A 的旧二进制代表当前代码。
