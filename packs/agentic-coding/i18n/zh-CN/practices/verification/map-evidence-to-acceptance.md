# 把每项验收要求对应到实际检查结果

## 适用场景

检查已经有结果，准备判断用户要求是否都已满足时，先把每个结果放到它实际证明的验收条件旁边。这里用的是已有结果，不是实现前的检查计划。旧结果是否仍适用于当前文件和条件，需要另行判断；对照后发现没有覆盖的要求，再决定怎么处理。

## 具体指导

1. 从用户请求、已接受 issue 或规格复制当前验收准则，每条承诺行为一行。
2. 把每个收集到的结果——测试输出、检查过的文件、直接观察或通过的命令——放到它实际检查过的验收条件旁边，写明覆盖的行为和环境。
3. 把其余每行标为"未覆盖"或"部分覆盖"。只有实际观察到了多项要求各自的结果，一份检查结果才可以支撑多条验收条件。
4. 单独记录强制性门槛并标注其角色，即使它不证明任何用户能力。

只有实际观察过某项承诺行为的结果，才能为该行为提供证据。列好逐项对应的表格后停止；不要用信心、测试数量或其他检查的成功填满空行。

## 反模式

用户要求预订提交在请求重试时仍只生成一个预约。仓库有绿色的计算测试、完整构建、静态检查和一次成功的预订演示。日志可观、每条命令都是绿的，Agent 报告验证完成。但这些结果没有一个重试过提交，"不重复"的要求消失在活动摘要背后。

## 原因

命令通过，不代表它检查了名字看起来涵盖的一切。列清哪份结果证明哪条要求，才能看出证据的限制和缺口。评审者也能针对这层关系提出问题，不必从长日志里猜测是否满足验收。

## 例外与边界

一次端到端观察确实包含多条验收条件时，可以同时覆盖它们；不必为凑"一行一结果"重复劳动。用户请求、已接受 issue 和规格对验收有分歧时，先询问应以哪份来源为准，不要自行编造验收条件。本 Practice 产出对照表，不负责最终交付措辞。

## 示例

用户要求报告字段齐全、页面可读、文件能在目标手机上打开。仓库有 schema 测试、渲染页面截图、成功的手机下载和打开记录，以及通过的构建。Agent 把结果与验收条件逐项对应：schema 结果覆盖必填字段，图像检查覆盖可读性，手机观察覆盖投递与打开；构建只记录为必需门槛。没有检查中断后恢复下载，就明确保留离线重试未覆盖的状态。
