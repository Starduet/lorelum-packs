# 确认纠正后把工作复位到权威基线

## 适用场景

经授权的用户纠正、已接受的范围变更或对未请求行为的否决，使当前工作的一部分过时之后使用。把旧解释从仍在塑造目标、计划、代码、测试或文档的地方清除。来源仍有冲突时，先解决"听谁的"。未经验证的评审意见也不是已确认的纠正。

## 具体指导

1. 重读纠正内容和当前请求或规格，用一句话说出纠正后的方向。
2. 找出唯一依据是被拒解释的假设和产物——目标句、计划项、代码、测试、文档——移除或修订它们。
3. 保留有独立需求或风险依据的行为和保护；纠正不是丢弃整个实现的许可。
4. 不要把这次否决转成新的永久测试、规则或禁令，除非授权来源明确建立了它。

以"一份当前的请求工作说明，区分恢复的范围与纠正引入的真正新范围"结束。

## 反模式

用户要求移除 Agent 无设计依据添加的辅助文案。Agent 移除了它，然后又加了否定测试、注释和一条禁止所有类似界面出现辅助文案的设计规则。这个回应看起来有保护性，却把一次清理变成了用户从未请求的新产品契约。

## 原因

纠正的失败方式是过期推理残留在计划、测试或文档里。复位所有受影响工作能移除这种影响，同时不犯相反的错误：把一次被拒的尝试变成长期禁令。

## 例外与边界

授权来源明确说明时，纠正可以建立新的持久契约。安全、隐私、合规、数据完整性或兼容性也可以为持久保护提供独立理由。

## 示例

用户澄清要求的状态是屏幕上的徽标，不是 Agent 从相邻功能推断的每周邮件。Agent 移除调度器、邮件代码和邮件专属测试，保留徽标，并且不记录任何针对未来通知工作的通用禁令。
