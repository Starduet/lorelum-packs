# 先弄清要解决什么，再制定计划和标准

## 适用场景

写计划、验收标准、评审检查单、测试清单、校验或权限规则、评分表时，都要决定哪些条目值得放进去。这些条目会影响做什么、什么算通过、允许谁做什么，或怎样给候选结果打分。

不论是从第一条开始写、修改已有清单，还是接手一份越积越长的清单，都先弄清它要解决哪些问题、满足哪些要求。笔记、盘点和大纲如果只是记录或探索想法，还没有用来作这些决定，就不必按这套方法处理。

## 具体指导

1. 先写清这份清单要判断什么：验收时必须区分哪些结果，证据表明哪些失败确实可能发生，有权决定的人又明确提出了哪些扩展。只为这些需要提出条目。
2. 逐项看它增加了什么。它是否补上了一个尚未覆盖的问题？它会改变做还是推迟、接受还是拒绝，或让两份合理产出得到不同分数吗？已有条目如果在判断同一件事，就合并，不要重复保留。
3. 记录必要的取舍：既要覆盖重要问题，也要让清单用得起来；分清当前要求和已提出的扩展；保留防护，但不要使工作无法进行。有人提议加一条时，先问它解决什么。不会改变任何决定的条目，暂不纳入。
4. 接手旧清单时，先找出每条原本为什么要加，再按这些问题和要求重新整理。找不到依据的条目可以删除。

已列出的问题和要求都有条目覆盖、每条都会影响决定、重复项已经合并，而且每条不通过时该怎么办也已说清，清单就可以定下来了。之后再增加条目，需要有新问题或新要求。小改动如果不需要计划，直接依据目标和验收条件处理即可，不必另做一套推导。

## 反模式

团队的数据迁移评审最初只有三条检查。每次事故后都加一条听起来合理的要求，直到每个迁移都会被某项检查挡住，评审者花几周争论例外。团队随后大幅删减，又漏掉了最初引发事故的检查。两次都只调整清单长短，没有写清它到底要防止哪些问题。

## 原因

多加一条检查，很容易说出好处；删掉一条，又像是在放弃防护。清单就这样越积越长，最后难以使用。应当反过来，从问题决定条目：重要情况没检查到就补上，几条标准反复衡量同一件事、分散了权重就合并。只按条目数量增删，会反复陷入扩张和删减。

## 例外与边界

适用的契约、政策或合规规定要求保留某项检查时，即使在本地说不清理由，也要注明来源并保留。探索想法的列表可以先作为草稿，等到要据此作决定时再整理。

这里解决清单该有哪些内容。计划里的工作流能不能走完，仍要实际走查；某项工作是否属于本次范围，也需要另行判断。

## 示例

团队准备给数据库 schema 迁移制定上线标准。他们需要能回滚变更、保住已有数据，并在出错时及时发现。因此列出四项：经过测试的回滚方法、迁移后数据行的完整性检查、切换期间写入失败的告警，以及中止迁移的条件。评审者又提出检查迁移文件的代码风格。团队暂不纳入：它没有解决已列出的问题，也不会改变“继续上线还是中止”的决定。
