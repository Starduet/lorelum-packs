# 按失败代价决定投入多少工程工作

## 适用场景

为选定方案设定初始工程深度时使用。考虑失败会影响多少用户或系统、变更是否可逆、还有哪些未知、以及恢复成本。它确定调查、验证、审查和恢复准备的整体深度；为每条验收条件选择观察方式是下一步的证据规划决策。如果实现已经揭示新的风险或范围，应改为基于那些事实重做计划。

## 具体指导

1. 找出本变更失败时的可信伤害：影响哪些用户或系统，暴露哪些数据、安全、兼容性或运维问题，以及变更能否撤销。
2. 评估驱动因素——受影响用户、可逆性、剩余不确定性、失败代价——并选择成比例的深度。可逆的改色和线上 schema 变更不配同样的"一个测试"待遇。
3. 让每个保护措施对应一个失败模式或强制政策，删掉没有这种理由的仪式；把保护措施自身的代价也算进去：误拒、变慢的失败、额外配置、阻塞升级或修复、维护成本。
4. 如果某个实质风险未知，在敲定深度之前先调查或做一次有界探测；点名未决事实和会改变计划的结果。

当每个保护措施在实际失败画像中都有理由、且一句话能回答"这个变更值得多深的验证和恢复投入"时停止。有清晰报错的可恢复失败，可能比改变结果的兜底需要更少的机制。

## 反模式

团队的上一个项目是鉴权迁移，于是 Agent 把它的灰度计划、大回归套件和回退清单照搬到一次可逆的样式修正上。后来，同样熟悉的"聚焦测试"模板又被用在可能搁置线上数据的 schema 变更上。划一的流程看起来一致，却在两个方向上都错了。

## 原因

成比例的投入把力气导向要紧的失败。它既避免在廉价变更上过度设计，也避免在失败昂贵或难以逆转时因小失大。

## 例外与边界

组织政策可能无视局部风险强制要求评审或检查。未知的安全、隐私或数据丢失暴露，在可能实质改变决策时应做有界调查。不确定性不是穷举无限假想攻击者、损坏模式或恢复框架的许可。

## 示例

修改 webhook 签名格式可能弄断每个现有接收方并阻断投递。计划因此包含新旧兼容检查、代表性消费方测试、分阶段切换和回退路径。这些保护由受影响的现有接收方数量证明合理，而不是由"每个请求变更都要同样仪式"的规则证明。同一个迭代里那次可逆的改色，一次聚焦检查加评审就够了。
