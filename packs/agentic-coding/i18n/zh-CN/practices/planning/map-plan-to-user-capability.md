# 顺着用户的操作，检查计划有没有漏步骤

## 适用场景

一项功能要经过界面、服务、存储或规则处理等多个部分时，定下计划前，顺着用户的操作从头走到尾，看任务清单是否覆盖了整件事。内部重构也要检查，只是这里追踪的是必须保持不变的行为。已经做完、正在对照验收结果时，应检查已有证据覆盖了什么，而不是重新检查计划。

## 具体指导

1. 从用户描述的操作和期待看到的结果出发，看任务清单能否把两者接起来。
2. 逐步经过入口、服务之间的调用、状态变化和必须遵守的规则，直到得到那个结果。界面或 API 写好了，不等于整件事已经完成。
3. 给每一步找到计划中负责实现它的任务，列出没人安排去做的必需步骤。
4. 补上缺失工作，或明确说明本次承诺交付的范围缩小了。已列出的组件都完成，不代表需要的工作都列出来了。

计划能从发起操作一直走到预期结果，没有无法解释的必需步骤缺失，就可以结束这项检查。

## 反模式

库存调拨计划安排了请求接口和确认页面，两者都容易开发和测试。但中间的库存预留由另一个服务负责，没人把它列进计划。于是清单上的任务全都能完成，两个操作员却仍然可能同时卖出同一批库存。

## 原因

逐个看任务，容易觉得每个组件都已经安排好了，却漏掉组件之间的工作。把完整操作走一遍，才能在动手之前发现缺口，避免做到一半再花更大代价补上。

## 例外与边界

可以分批交付，只做完整功能的一部分，但要明确说明本次限制。基础设施和重构工作，应沿着必须保留的实际运行行为检查，不必为了套用方法而虚构用户。

## 示例

仓库已经能创建和校验重置密码的令牌，只围绕令牌安排任务，看起来就差不多了。Agent 从用户请求重置开始，依次检查消息送达、令牌校验、密码更新和按要求使旧会话失效，才发现后两步根本没有对应任务。于是先补进计划，再动手，而不是把令牌服务当作完整的账户恢复功能。
