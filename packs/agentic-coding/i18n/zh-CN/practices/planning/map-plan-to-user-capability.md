# 按用户完成的整条能力来检查计划

## 适用场景

当计划跨越接口、服务、存储、策略或其他边界、可能遗漏请求路径的一部分时使用。对内部重构，映射必须保持不变的行为。如果实现已经完成、需要把收集到的结果与验收对照，应改为映射证据。

## 具体指导

1. 点名发起动作和请求者描述的可观察结果，然后把任务清单当作从一端到另一端的路径来读。
2. 逐步走完这条路径：入口、服务交接、状态变更、策略，以及用户观察到的结果。界面和 API 是路径上的站点，不是终点。
3. 把路径的每一步指派给计划中的某个任务，列出没有任何任务覆盖的必需步骤。
4. 对每个未被覆盖的步骤，把缺失的职责补进计划，或显式收窄承诺的能力。各层完成不证明路径完整。

当这张映射能把动作与结果连接起来、没有无法解释的必需缺口时停止。

## 反模式

一个库存调拨计划包含请求端点和确认界面，两者都好建好测。它遗漏了两者之间的库存预留，因为该职责在另一个服务里。列出的每个任务都能完成，而两个操作员仍然可以把同一批库存超卖。

## 原因

技术任务清单奖励局部完成。一张"行动者到结果"的映射能在部分实现让缺口变得昂贵之前暴露缺失的交接。

## 例外与边界

计划中的部分交付可以只覆盖能力的一部分，前提是该限制是显式的。基础设施和重构工作应映射到它们保全的运维行为，而不是虚构一个用户。

## 示例

密码重置任务进入一个已有令牌创建和校验的仓库，令牌-only 的计划看起来接近完整。Agent 把请求、消息送达、令牌校验、密码更新和必需的会话失效映射到"安全恢复账户"。更新和失效两步没有任务覆盖，于是动手前先补上，而不是把令牌服务当作全部能力。
