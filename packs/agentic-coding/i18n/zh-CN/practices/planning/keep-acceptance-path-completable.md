# 加上检查后，用户仍要能完成操作

## 适用场景

一个操作要经过多项检查时，不能只看每项是否合理，还要看它们放在一起会不会让用户无法完成任务。规划或实现时，把正常操作、启动、停止，以及受支持的修复和恢复命令走一遍；出错、重复调用、重新打开的情况也要包括。即使任务没提到检查或审批，也要看新增要求会不会挡住这些操作。

如果只是在判断某一项检查有没有必要，参照
`justify-added-checks`。这里要确认的是：整个操作没有漏掉必需步骤，而且加上这些检查后仍能走完。

## 具体指导

1. 从用户发起操作开始，一直走到验收要求中应看到的结果，把新增检查都放进去。先确认每个必需步骤由哪个组件或人员负责，再决定检查多严格。
2. 找出会拒绝、拖延或打断操作的新增检查。能只记日志就不必阻止操作；也可以在结果上标注限制、请求一次确认，或确有必要时直接拒绝。处理方式必须能解决某个具体失败。要采取比记日志更严格的措施，先根据当前部署的事实或要求，说明谁能造成这种失败、通过什么操作触发。只说“存在某类风险”或“攻击者可能这么做”还不够。能只检查有风险的情况，就不要限制整个操作。
3. 逐项问：去掉这项新增检查，究竟会坏在哪里，影响谁？答不出就移除。无人能回答的确认框，实际上是在阻止操作；应改用更轻的处理方式，或缩小检查范围，并写清其他情况怎样跳过它。
4. 看最容易失败的检查不通过时会怎样。尽量让它只影响自己，并说明其他哪些结果仍可使用。如果一次失败必须让所有已通过的结果都作废，要说明谁需要这个规则，以及为什么标明来源或提供部分结果仍会误导。
5. 在相应计划条目旁，写下这项检查针对什么失败、失败时怎样处理。

每条验收要求都能完成，不再要求用户做验收或适用政策之外的额外操作，且每项新增检查的处理方式都有理由，就可以结束。小改动不必另写计划，只需判断新增检查会不会阻断或拖延必需操作，以及哪种失败或强制政策要求这样做。正当的拒绝要保留；否则减轻限制、缩小范围或不加这项检查。

修复命令必须能在需要修复的状态下运行：重建损坏索引，不能先要求索引健康；停止已确认身份的旧进程，也不必先让旧进程的业务 API 兼容新客户端。但操作所需的授权、进程身份、运行状态保护和一致性要求仍要保留。必需保障与承诺的恢复方式冲突时，应说明冲突，不要为了让命令成功而绕过保障。

## 反模式

任务给本地 CLI 加一个 config-set 命令。Agent 连同键 allowlist、路径穿越校验、属主权限检查和每次写入确认一起交付。验收场景——开发者跑命令、配置更新——从此需要请求从未提过的交互和授权，而且调用该 CLI 的脚本无法回答确认。直到交付后，Agent 才通过删除不必要的检查来调整防护。

## 原因

单独看，每项检查都像是在防止事故；放在一起，却可能让整个操作无法完成。只关注它能挡住的事故，就容易忽略不断加检查的代价。因此要分别看有没有漏步骤、增加了哪些打断，以及单项失败会怎样影响其他结果。检查好其中一项，不能代替另外两项。

## 例外与边界

适用的政策或合规规定可能强制要求某项检查，即使本地不会发生相应失败，也要注明来源并保留。确实可达的威胁也可以成为拒绝操作的理由；这里不是让人删掉正当保障。

既有系统防护应当视为必须遵守的条件，不能按“去掉会怎样”的方法随意删除。它们使必需操作无法完成时，应提出冲突。检查该放在哪个组件、是否与其他检查重复，是另外两个问题。

## 示例

为 config-set 设计检查时，先走一遍“运行命令、检查允许修改的键、检查权限、确认、写入、验证”的完整过程，再问去掉每项新增检查会怎样。路径穿越输入不会进入路径处理，操作系统已经限制文件属主权限，确认框拦截的笔误又不在验收要求内，这些检查可以删除或减轻限制。但已有证据表明，覆盖 security-token 键会迫使其他地方重新认证。因此只对这类键保留一次确认；其他键直接写入，并记录变更。

后端修复命令必须能在服务未就绪时重建损坏的派生索引。提议复用的 readiness 预检却会在修复开始前拒绝这一状态。Agent 为普通查询保留就绪要求，为修复提供单独的授权路径和必需的互斥修改保护。修复不必先成功查询索引就能重建；未授权调用方或冲突的 writer 仍被拒绝。不引入全局“跳过检查”开关。
